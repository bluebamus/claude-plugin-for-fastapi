stage-pilot 사용 매뉴얼

stage-pilot은 FastAPI 프로젝트를 단계별 워크플로로 이끄는 Claude Code 플러그인입니다. 빈 폴더에서 새 프로젝트를 시작할 때도, 이미 돌아가는 레거시 프로젝트에 기능을 더하거나 구조를 고치거나 성능을 끌어올릴 때도, "지금 단계에서 어떤 플러그인을 어떤 순서로 쓰고, 어디서 멈춰 확인받고, 무엇으로 끝났다고 판단하는가"를 알려 주고, 원하면 그 플러그인을 직접 호출해 단계를 수행합니다.

이 문서는 처음 쓰는 사람이 설치부터 자동 수행까지 혼자 따라 할 수 있도록 썼습니다. 개념 → 설치 → 빠른 시작 → 트랙별 단계 설명 → 명령·모드 → 전체 단계 표 → 검증 결과 → 문제 해결 순서로 읽으면 됩니다.

1. stage-pilot이란

풀려는 문제

통합 가이드는 Claude Code 플러그인 20여 개를 고르고, 레거시 FastAPI 프로젝트를 0~11단계로 나눠 단계마다 쓸 플러그인과 확인 지점을 정해 두었습니다. 그런데 실제로 일할 때는 다음이 어렵습니다.

  • 지금 몇 단계인지, 이 단계에서 무엇을 써야 하는지를 매번 문서에서 다시 찾아야 합니다.
  • 플러그인 이름을 알아도 스킬인지, 에이전트인지, 명령인지에 따라 부르는 방법이 다릅니다.
  • 작업에 몰입하다 보면 단계를 건너뛰거나, 확인받을 지점을 지나치거나, 끝나지 않은 단계를 끝났다고 여기기 쉽습니다.
  • 가이드는 기존 코드를 고치는 경우만 다룹니다. 아무것도 없는 상태에서 기획·설계·기술 선정·작업 계획부터 시작하는 경우나, 리팩토링이 아닌 기능 추가·고도화는 어떤 플러그인을 어떤 순서로 쓸지 정해져 있지 않습니다.

stage-pilot이 하는 일

트랙 고르기

프로젝트 폴더가 비어 있는지, 코드가 있는지 보고 요청의 의도(새 프로젝트, 기능 추가, 리팩토링, 고도화)와 맞춰 알맞은 트랙을 추천합니다.

제안

현재 단계의 주 플러그인·보조 플러그인·조건부 플러그인, 실행 순서, 멈출 곳, 완료 기준을 한 장의 "단계 카드"로 보여 줍니다. 설치되지 않은 플러그인은 설치 명령까지 알려 줍니다.

수행

단계 카드의 실행 순서대로 스킬·에이전트·명령을 실제로 호출해 작업합니다. 기본은 승인 지점에서 멈추고, 자동 승인 모드에서는 정해진 원칙으로 결정하며 끝까지 진행합니다.

완료 확인

단계마다 정해 둔 조건(문서 내용, 요구사항 ID가 계획·테스트까지 이어지는지, 테스트 통과, 작업 트리 정리)을 스크립트로 확인합니다. 통과해야 다음 단계로 넘어갑니다.

감시

대화 중 요청이 다른 단계의 일이면 "이 요청은 9단계, 현재는 4단계"라고 짚어 줍니다. 건너뛰기를 막지는 않고, 알고 고르게 합니다.

기록

현재 단계, 거쳐 온 단계, 자동으로 내린 결정과 근거, 단계마다 무엇을 호출하고 무엇이 나왔는지를 프로젝트 안에 남깁니다. 세션을 다시 열어도, 다른 사람이 이어받아도 이어서 작업할 수 있습니다.

한눈에 보는 흐름

요청
"새 프로젝트 시작" / "기능 추가"→ 트랙 추천·시작
init <트랙>→ run
플러그인 호출·작업→ 승인 지점
확인 또는 자동 결정→ 단계 보고서·check→ next

신규 트랙으로 만든 프로젝트는 끝나는 순간 "레거시"가 됩니다. 이어서 기능 추가, 리팩토링, 고도화 트랙을 같은 상태 파일 위에서 차례로 진행할 수 있습니다.

2. 먼저 알아 둘 개념

트랙 (= 프로필, profile)
어떤 종류의 작업을 하는지에 따라 정해진 단계 묶음입니다. 신규 프로젝트용 greenfield, 레거시용 feature(기능 추가)·default(리팩토링)·enhance(고도화)가 있습니다. 특정 프로젝트 전용 트랙은 없습니다 — 어떤 FastAPI 프로젝트에도 같은 트랙을 씁니다. 자세한 비교는 5. 트랙 고르기에 있습니다.
단계 (stage)
트랙 안의 한 구간입니다. id는 0, 1 … 이고, 리팩토링 트랙에는 진입 전 매뉴얼 단계 pre가, 시나리오 트랙에는 4-7처럼 묶은 id가 있습니다.
단계 카드
한 단계의 정보를 모은 요약입니다. 주 플러그인, 보조 플러그인, 조건부 플러그인, 실행 순서(run), 승인 지점, 완료 기준, 완료 확인 목록, 현재 모드, 미설치 플러그인, 다음 단계가 들어 있습니다.
주 · 보조 · 조건부 플러그인
주는 그 단계의 핵심 도구, 보조는 함께 쓰면 좋은 도구, 조건부는 조건이 맞을 때만 쓰는 도구입니다. 예: context7은 외부 문서 조회가 허용됐을 때만, playwright는 Jinja 화면이 있을 때만 씁니다.
실행 항목 (run)
단계에서 순서대로 할 일입니다. 종류는 여섯 가지입니다.
종류뜻stage-pilot이 처리하는 방법
skillClaude가 불러와 따르는 작업 지침Skill 도구로 호출 (예: superpowers:writing-plans)
agent별도 컨텍스트에서 일하는 전문 작업자Agent 도구로 호출 (예: feature-dev:code-architect). 서로 독립인 것은 병렬로
command플러그인의 슬래시 명령Skill 도구로 플러그인:명령 이름을 호출 (예: commit-commands:commit)
mcp플러그인이 제공하는 MCP 서버의 도구그 서버의 도구를 호출 (예: context7로 라이브러리 문서 조회)
shell터미널 명령Bash로 실행. 파일을 바꾸는 명령은 제안 모드에서 먼저 보여 줌
user사람만 실행할 수 있는 명령실행하지 않고 그대로 보여 줌 (/plugin, /mcp, /ralph-loop 등)
조건부 실행 항목 (when)
조건이 맞을 때만 하는 실행 항목입니다. 예를 들어 구현 단계의 superpowers:dispatching-parallel-agents는 "선행 관계가 없는 작업 묶음이 2개 이상일 때"만 씁니다. stage-pilot은 프로젝트와 문서를 보고 조건을 판정하고, 쓰지 않을 때는 그 근거를 기록합니다.
승인 지점 (approval)
사람이 결정해야 하는 곳입니다. 예: "설계안 선택", "영역별 기술 선택". 기본 모드에서는 여기서 멈춥니다.
완료 기준 (done)과 완료 확인 (check)
완료 기준은 사람이 읽는 조건이고, 완료 확인은 그중 스크립트로 확인할 수 있는 부분입니다. 예: 작업 계획 단계는 "모든 요구사항 ID가 작업표에 있는가"를 실제로 대조합니다. 자세한 내용은 12장에 있습니다.
단계 보고서
단계를 마칠 때마다 남기는 짧은 문서입니다(docs/stage-pilot/<작업>/<트랙>-<단계>.md). 호출한 플러그인과 결과, 산출물, 결정, 완료 기준 충족 여부가 들어갑니다.
문서 ID
단계 사이를 잇는 번호입니다. 요구사항 R-1, 비기능 요구 NFR-1, 기능 추가 요구 F-1, 고도화 목표 E-1, 작업 T-1. 뒤 단계 문서와 테스트가 앞 단계 ID를 인용하므로, 빠진 요구사항이 없는지 기계적으로 확인할 수 있습니다.
모드
제안 모드(기본): 알려 주기만 합니다. 수행: run을 입력하면 플러그인을 호출해 작업하되 승인 지점에서 멈춥니다. 자동 승인 모드: auto on이면 승인 지점에서 멈추지 않고 정해진 원칙으로 결정하며 끝까지 진행합니다.

3. 설치

준비물

  • Claude Code (CLI, 데스크톱, IDE 확장 중 하나)
  • Node.js 18 이상 — 훅과 상태 스크립트가 Node.js 표준 라이브러리만으로 동작합니다. 별도 npm 패키지는 필요 없습니다.
  • Git — 신규 트랙의 준비 단계와 커밋 단계에서 씁니다.
  • Python 3.12 — 만들거나 고칠 FastAPI 프로젝트용입니다. 신규 트랙은 프로젝트 폴더 안에 .venv를 만들어 씁니다.
  • stage-pilot이 호출할 플러그인 — 아래 목록을 설치해 두어야 수행 모드가 실제로 호출할 수 있습니다. 없어도 제안 모드는 동작하며, 카드에 설치 명령이 나옵니다.

마켓플레이스로 설치 (권장)

/plugin marketplace add bluebamus/claude-plugin-for-fastapi
/plugin install stage-pilot@claude-plugin-for-fastapi

저장소를 클론해 두었다면 GitHub 주소 대신 로컬 경로를 써도 됩니다: /plugin marketplace add C:/work/claude-plugin-for-fastapi

claude --plugin-dir C:/work/claude-plugin-for-fastapi/plugins/stage-pilot

설치 확인

  1. Claude Code에서 /stage-pilot:stage profiles를 입력합니다.
  2. greenfield, feature, enhance, default 네 줄이 나오면 설치된 것입니다.

업데이트와 제거

이 마켓플레이스는 자동 업데이트가 기본으로 꺼져 있습니다. 새 버전은 다음 중 하나로 받습니다.

  • 한 번에: /plugin → Marketplaces 탭 → claude-plugin-for-fastapi → Update marketplace. 목록을 새로 받고, 여기서 설치한 플러그인도 함께 업데이트합니다.
  • 플러그인 하나만: /plugin → Installed 탭 → 플러그인 → Update now, 또는 셸에서 claude plugin update stage-pilot@claude-plugin-for-fastapi.
  • 자동으로: Marketplaces 탭에서 이 마켓플레이스를 고르고 Enable auto-update를 켭니다.

업데이트 뒤에는 /reload-plugins를 실행하거나 세션을 다시 엽니다.

/plugin marketplace update claude-plugin-for-fastapi        # 마켓플레이스 목록만 새로 받기 (설치된 플러그인은 그대로)
/plugin uninstall stage-pilot@claude-plugin-for-fastapi     # 플러그인 제거
/plugin marketplace remove claude-plugin-for-fastapi        # 마켓플레이스 등록 해제 (여기서 설치한 플러그인도 제거)
마켓플레이스는 등록한 브랜치만 따라갑니다. #php 없이 등록했다면 업데이트해도 기본 브랜치 main을 받고, #php로 등록했다면 php 브랜치를 받습니다. 판을 바꾸려면 아래 「PHP 지원판」 절처럼 지우고 다시 등록합니다.

여러 세션에 적용하기

같은 프로젝트에서 Claude Code 세션을 여러 개 띄워 두었다면, 한 세션에서 설치한 플러그인을 다른 세션에서 다시 설치할 필요는 없습니다. 설치 기록은 설정 파일에 남고 같은 컴퓨터의 모든 세션이 그 파일을 읽습니다. 다만 이미 실행 중인 세션은 시작할 때 불러온 플러그인을 계속 쓰므로, 나머지 세션마다 다시 불러오기만 하면 됩니다.

/reload-plugins
  • 프롬프트 캐시가 무효화된다는 경고와 함께 적용이 보류되면 /reload-plugins --force를 실행합니다(캐시 없는 요청 1회 비용).
  • 적용 확인: /를 입력해 /stage-pilot:stage가 보이거나, /plugin의 Installed 탭에 나오면 됩니다.
  • 세션을 유지할 필요가 없다면 종료 후 다시 시작해도 같습니다.

적용되지 않으면 설치 범위를 확인합니다. 범위는 /plugin의 Installed 탭이나 셸의 claude plugin list에 나오는 Scope 줄에서 봅니다.

설치 범위기록 위치보이는 세션
사용자 (user)~/.claude/settings.json이 컴퓨터의 모든 프로젝트, 모든 세션
프로젝트 (project)<프로젝트>/.claude/settings.json같은 폴더에서 실행한 세션
로컬 (local)<프로젝트>/.claude/settings.local.json같은 폴더에서 실행한 세션

일부 세션이 git worktree(예: .claude/worktrees/...)에서 돌고 있다면 그 세션의 작업 폴더는 원래 프로젝트와 다르므로, 프로젝트·로컬 범위로 설치한 플러그인이 보이지 않습니다. /plugin의 Installed 탭에서 지우고 Install for you (user scope)로 다시 설치하는 것이 가장 간단합니다. 프로젝트 범위를 유지하려면 바뀐 .claude/settings.json을 커밋해 각 worktree에도 들어가게 합니다.

PHP 지원판 설치 (php 브랜치)

이 매뉴얼은 php 브랜치의 PHP 지원판을 설명합니다. 어느 판인지는 버전 번호가 아니라 /plugin의 Marketplaces 탭에 보이는 등록 출처로 구분합니다(...#php면 PHP 지원판). 마켓플레이스 주소 뒤에 #php를 붙이면 기본 브랜치 대신 php 브랜치에서 플러그인을 받습니다. 위의 「마켓플레이스로 설치」 명령은 기본 브랜치 main(PHP 미지원판)을 설치합니다.

PHP 프로젝트를 다룰 때는 준비물에 PHP, Composer, PHPUnit이 더해집니다. 완료 확인이 vendor/bin/phpunit을 찾으므로 composer require --dev phpunit/phpunit으로 설치해 둡니다.

기본판을 이미 설치했다면 업데이트로는 바뀌지 않습니다. 마켓플레이스는 등록할 때 정한 브랜치만 따라가고, 등록한 브랜치만 바꾸는 명령은 없습니다. 두 판은 마켓플레이스 이름(claude-plugin-for-fastapi)이 같아 함께 등록할 수도 없습니다. 그래서 기존 마켓플레이스를 지우고 #php로 다시 등록한 뒤 설치합니다. 마켓플레이스를 지우면 거기서 설치한 플러그인도 함께 제거됩니다. 처음 설치한다면 아래 각 방법의 remove 줄만 건너뜁니다.

방법 A. Claude Code 세션 안에서 (권장)

/plugin marketplace remove claude-plugin-for-fastapi
/plugin marketplace add bluebamus/claude-plugin-for-fastapi#php
/plugin install stage-pilot@claude-plugin-for-fastapi
/plugin install legacy-onboarding-manual@claude-plugin-for-fastapi

install 줄은 플러그인 정보 화면을 엽니다. 설치 범위(사용자·프로젝트·로컬)는 예전과 같은 범위를 고릅니다. 안내가 나오면 /reload-plugins를 실행합니다.

방법 B. 셸에서 (세션 밖, 스크립트용)

claude plugin marketplace remove claude-plugin-for-fastapi
claude plugin marketplace add bluebamus/claude-plugin-for-fastapi#php
claude plugin install stage-pilot@claude-plugin-for-fastapi
claude plugin install legacy-onboarding-manual@claude-plugin-for-fastapi

기본 범위는 사용자 범위입니다. 프로젝트 범위로 설치했었다면 install 줄에 --scope project를 붙입니다. 다음 세션부터, 또는 열린 세션에서 /reload-plugins를 실행한 뒤부터 적용됩니다.

방법 C. 로컬 클론으로 (판을 자주 바꿀 때)

git clone -b php https://github.com/bluebamus/claude-plugin-for-fastapi C:/work/claude-plugin-for-fastapi
/plugin marketplace remove claude-plugin-for-fastapi
/plugin marketplace add C:/work/claude-plugin-for-fastapi
/plugin install stage-pilot@claude-plugin-for-fastapi
/plugin install legacy-onboarding-manual@claude-plugin-for-fastapi

로컬 경로로 등록한 마켓플레이스는 폴더의 파일을 바로 읽습니다. 이후에는 지우고 다시 설치할 필요 없이, 그 폴더에서 git checkout php 또는 git checkout main으로 판을 바꾸고 /reload-plugins만 하면 됩니다. GitHub의 새 버전은 그 폴더에서 git pull로 받습니다.

바뀌었는지 확인

  1. 설치된 버전은 /plugin의 Installed 탭이나 셸의 claude plugin list에서 봅니다. 두 판은 버전을 각자 올리므로 버전 번호로 판을 구분하지는 않습니다.
  2. /plugin의 Marketplaces 탭에서 claude-plugin-for-fastapi의 출처가 ...#php(방법 C는 로컬 경로)로 보여야 합니다.

참고

  • 작업 기록은 남습니다. 마켓플레이스를 지워도 프로젝트의 .claude/stage-pilot/state.json과 docs/의 단계 문서는 그대로라, 다시 설치한 뒤 하던 트랙을 이어갈 수 있습니다.
  • 프로젝트 범위 설정도 그대로 쓰입니다. .claude/settings.json에 기록된 플러그인 이름이 같으므로 다시 설치한 뒤 그대로 적용됩니다.
  • 기본판으로 돌아가려면 같은 방법으로 마켓플레이스를 지우고 #php 없이 다시 등록해 설치합니다.
  • PHP 프로젝트에서 쓰는 방법은 7장 「PHP·CodeIgniter 프로젝트에서 쓰기」에 있습니다.

2단계 — 설계: 아키텍처·도메인 모델·API

목적. 요구사항을 모두 덮는 가장 단순한 구조를 정합니다.

  • feature-dev:code-architect(에이전트) — 레이어 구조, 도메인 모델, API, 트랜잭션 경계를 담은 설계안 2~3개를 냅니다.
  • code-modernization:architecture-critic(에이전트) — 요구사항에 비해 과한 계층·추상화가 없는지 비평합니다.

완료 확인. ERD·API·트랜잭션 내용이 있고, 요구사항 문서의 모든 R-가 설계 문서에 인용되어야 합니다.

3단계 — 기술 선정: 프레임워크별 라이브러리·버전

  • context7(MCP, 조건부) — 외부 문서 조회가 허용됐을 때만, 후보 라이브러리의 현재 안정 버전과 권장 사용법을 조회합니다. 허용되지 않았으면 호출하지 않고 "조건 불충족"으로 기록합니다.
  • code-modernization:architecture-critic(에이전트) — 선정안이 요구사항에 비해 과한지 검토합니다. 예: 동시 사용자가 적은 사내 도구에 메시지 큐를 넣지 않습니다.

5단계 — 구현: 계획 실행(TDD)

  • superpowers:test-driven-development(스킬) — 작업마다 실패하는 테스트를 먼저 쓰고 통과시키는 순서를 지킵니다.

PHP·CodeIgniter 프로젝트에서 쓰기 0.3.3

PHP 지원판(3장 「PHP 지원판 설치」)은 PHP·CodeIgniter 레거시에서도 기능 추가·리팩토링·고도화 트랙을 끝까지 진행할 수 있게, 프로젝트 판별·ID 추적·테스트 실행을 PHP에 맞춥니다.

항목PHP 프로젝트에서 하는 일
프로젝트 판별 (detect).php 파일이 있으면 레거시로 봅니다. vendor/(Composer 의존성)는 세지 않습니다. PHP 파일이 파이썬 파일보다 많으면 훅이 "레거시(PHP N개, 테스트 M개, CodeIgniter 사용/미확인)"로 알립니다. CodeIgniter는 CodeIgniter, CI_Controller, CI_Model, CI_VERSION으로 알아봅니다
테스트 실행 (check)--test로 준 명령이 없고 vendor/bin/phpunit이 있으면 php vendor/bin/phpunit을 씁니다. 다른 명령(예: CodeIgniter 4의 composer test, 특정 설정 파일)은 init … --test "<명령>"으로 줍니다
ID 추적요구사항 ID(R-·F-·E-)가 테스트까지 이어지는지 볼 때 *Test.php 파일과 tests/ 폴더 안의 .php 파일을 읽습니다. 테스트 메서드 이름이나 주석·docblock에 ID를 적습니다
온보딩 매뉴얼legacy-onboarding-manual 0.1.1의 검사 스크립트가 application/controllers/Board.php:42 같은 .php:줄 근거를 셉니다

}
신규 트랙은 FastAPI 전용입니다. greenfield는 .gitignore의 .venv와 fastapi 의존성을 확인하므로 PHP 프로젝트를 새로 만들 때는 쓰지 않습니다. PHP 프로젝트는 기능 추가·리팩토링·고도화 트랙을 씁니다. 리팩토링 트랙의 안내(종료 전 테스트 규칙, --source 소스 폴더)는 0.3.6부터 언어 중립이라 CodeIgniter 3은 ./application, CodeIgniter 4는 ./app을 씁니다.
아직 Python·FastAPI 기준인 부분. 기술 선정 원칙(FastAPI + Pydantic + SQLAlchemy + pytest)과 일부 추천 플러그인(pyright-lsp, pydantic)은 그대로입니다. PHP 프로젝트에서는 Claude가 해당 항목을 건너뛰거나 같은 목적을 직접 수행하고, 단계 보고서에 fallback으로 기록합니다. 카드에 이 플러그인이 "미설치"로 보여도 PHP 작업에는 설치하지 않아도 됩니다. 단위 테스트로 확인한 지원이며, 실제 CodeIgniter 저장소로 하는 실전 평가는 아직 하지 않았습니다.

10. 수행 모드

/stage-pilot:stage run을 입력하거나 "4단계 진행해 줘", "현재 단계 진행해줘"처럼 분명히 요청하면, 카드의 실행 순서대로 플러그인을 실제로 호출해 작업합니다.

진행 순서

  1. 계획 받기 — stage.js plan으로 도구로 호출할 항목(invoke), 안내만 할 항목(other), 완료 확인 목록(checks), 단계 보고서 경로(report)를 받습니다.
  2. 플러그인 호출 — 스킬·명령은 Skill 도구로, 에이전트는 Agent 도구로, MCP는 그 서버의 도구로 부릅니다. 같은 일을 Claude가 직접 해 버리고 플러그인을 생략하지 않습니다. 정해진 도구가 실제로 쓰이게 하는 것이 이 플러그인의 목적이기 때문입니다.
  3. 메인 세션에서 직접 부르기 — 카드의 항목은 하위 에이전트(fork 포함) 안에서 부르지 않습니다. 하위 에이전트는 다시 에이전트를 만들 수 없습니다. 그래서 안에서 에이전트를 띄우는 명령(modernize-assess·modernize-harden·claude-security)은 그 안에서는 절차를 따르지 못합니다. 하위 에이전트에는 정리·검색 같은 보조 일만 맡깁니다.
  4. 결과를 받을 때까지 기다리기 — 에이전트나 워크플로를 백그라운드로 띄워 놓고 "기다리는 중"이라며 응답을 끝내지 않습니다. 비대화형 실행(claude -p)은 응답이 끝나면 세션도 끝나서 단계가 미완료로 남습니다.
  5. 분석 링크 legacy/<system> — modernize-preflight가 만드는 이 링크는 뒤 단계의 modernize-* 명령이 쓰므로 트랙 동안 둡니다. 링크가 프로젝트 자신을 가리키면 pytest·mypy가 같은 파일을 두 번 읽습니다. 그래서 check는 --ignore=legacy를 자동으로 붙이고, 직접 돌리는 도구에는 제외 옵션을 붙입니다. 링크는 트랙 마지막 단계에서 링크만 지웁니다. 재귀 삭제는 링크 너머 원본까지 지우므로 금지이고, Windows 정션은 cmd /c rmdir로 지웁니다.
  6. 문서 위치 맞추기 — 호출한 스킬이 자기 기본 위치(예: docs/superpowers/…)를 갖고 있어도, 카드에 적힌 위치(docs/project/…, docs/work/<작업>/…)에 저장합니다. 완료 확인이 그 위치를 읽기 때문입니다.
  7. 조건 판정 — when이 붙은 항목은 프로젝트를 보고 판정합니다. 조건이 맞지 않으면 호출하지 않고 "조건 불충족: 항목 — 근거"를 기록합니다.
  8. 재사용 — 리팩토링 트랙처럼 앞 단계(진입 전)와 뒤 단계(1·2단계)에 같은 분석 도구가 함께 놓인 경우, 이미 실행했고 그 뒤 코드가 바뀌지 않았으면 다시 돌리지 않고 "재사용: 항목 — 앞 단계·산출물·최신 확인 방법"을 남깁니다(stage.js reuse). 재사용은 수행으로 칩니다.
  9. 여러 번 쓰는 명령 — commit-commands:commit처럼 한 번에 하나를 만드는 명령은 논리 단위마다 다시 호출합니다. 절차는 따랐는데 완료 기준의 일부를 확인할 수단이 없으면(예: ruff 미설치) 대체 수행이 아니라 보고서에 "미확인 — 이유"로 적습니다.
  10. 사람에게 묻는 도구 —modernize-review(규칙 카드 판정), hookify(규칙 확인), skill-creator(평가 검토), brainstorming(질문)처럼 절차 중에 사람의 답을 받는 도구는, 자동 승인 모드에서 질문 대신 자동 결정 원칙으로 답해 그 도구의 절차와 산출물을 끝까지 채웁니다(예: 규칙 카드마다 "Not sure — 자동: 현재 동작을 계약으로 고정, 버그 후보"). 제안·수행 모드에서는 사람에게 그대로 묻습니다.
  11. 대체 수행 — 플러그인이 없거나 프로젝트 스킬(fastapi-layer-slice 등)이 아직 없으면, 같은 목적의 작업을 직접 하고 "대체 수행"으로 기록합니다. 스킬을 불러 놓고 그 절차를 따르지 않으면 호출한 것으로 치지 않습니다. 따를 수 없는 사정(필요한 도구나 실행 파일이 없음)이 있으면 그 이유와 해결 방법을 함께 남깁니다.
  12. 비용 동의 — 실행 전에 시간·토큰 비용 확인을 받는 스킬(예: claude-security의 스캔)은 사용자 본인의 말로 된 승인만 인정합니다. 자동 승인 모드라는 사실만으로는 승인이 아닙니다. 요청에 승인 문장이 있으면 원문 그대로 consent "<원문>"으로 기록하고, 스킬 인자 끝에 그 원문을 붙여 실행합니다. 기록이 없으면 비용이 드는 작업은 하지 않고 같은 목적의 다른 검토로 대체한 뒤 그 사실을 기록합니다. 제안·수행 모드에서는 스킬의 확인을 사용자에게 그대로 보입니다.
  13. 결과 반영 — 리뷰·분석 에이전트가 고칠 거리를 내면, 그 단계의 목표 범위 안에서 실제로 고칩니다. 리뷰 지적은 superpowers:receiving-code-review 기준으로 검증한 뒤 반영합니다.
  14. 승인 지점 — 결과를 요약하고 결정할 것을 묻고 멈춥니다(자동 승인 모드가 아닐 때).
  15. 단계 보고서와 완료 확인 — 보고서를 쓰고 check를 실행합니다. 통과하면 다음 단계로 갈지 묻고, 실패하면 빠진 것을 채운 뒤 다시 확인합니다.

.claude/ 쓰기가 거부될 때 — 승인 대기 초안

hookify 규칙, skill-creator로 만든 프로젝트 스킬 같은 파일은 프로젝트의 .claude/ 폴더에 저장됩니다. Claude Code는 이 폴더를 민감 경로로 보고 쓸 때마다 확인을 요구하며, 비대화형 실행(claude -p)에서는 거부합니다. 이때 stage-pilot은 다른 방법으로 우회하지 않고 다음과 같이 처리합니다.

  1. 같은 내용을 docs/stage-pilot/pending/ 아래, 원래 경로에서 .claude/를 뺀 위치에 둡니다. 예: .claude/hookify.block-remote-git.local.md → docs/stage-pilot/pending/hookify.block-remote-git.local.md, .claude/skills/fastapi-layer-slice/SKILL.md → docs/stage-pilot/pending/skills/fastapi-layer-slice/SKILL.md. 초안 경로에 .claude가 들어가면 그 경로도 민감 경로로 막히기 때문입니다.
  2. "승인 대기: 원래 경로 — 사용자 확인 후 옮김"을 결정 기록에 남깁니다.
  3. 완료 확인은 .claude/… 파일 대신 이 초안이 있어도 통과로 봅니다. 초안으로 남긴 것은 그 도구를 수행한 것이며 "대체 수행"이 아닙니다.

사람은 초안을 검토한 뒤 원래 위치로 옮기면 됩니다(대화형 세션에서 쓰기를 승인하거나 직접 복사).

11. 자동 승인 모드

자동 승인 모드에서는 승인 지점에서 멈추지 않습니다. 정해진 기본 원칙으로 결정하고, 그 결정과 근거를 상태 파일에 남긴 뒤 계속 진행합니다. 호출한 스킬이 사용자에게 질문하라고 해도(예: brainstorming) 질문하지 않고 의뢰서·코드·앞 단계 문서에서 답을 찾으며, 없으면 가장 보수적인 가정을 문서의 "가정" 절에 적습니다.

/stage-pilot:stage auto on          # 켜기
/stage-pilot:stage run --through 8  # 현재 단계부터 8단계까지 연속 수행
/stage-pilot:stage auto off         # 끄기

처음부터 자동으로 시작하려면 init greenfield --auto처럼 --auto를 붙이거나, 요청에 "자동 승인으로 진행해줘"를 넣습니다. 자동 모드는 next나 goto로 단계를 옮겨도 유지됩니다.

자동 결정 원칙

원칙은 모두 "요구에 없는 것을 더하지 않는 쪽, 동작을 바꾸지 않는 쪽, 범위를 좁히는 쪽"입니다.

결정할 일자동으로 고르는 것
요구사항 범위의뢰서에 있는 것만. 없는 기능은 넣지 않고 "범위 밖"에 적음. 모호하면 단순한 해석을 가정으로 기록
설계안요구사항을 모두 덮는 안 중 계층·추상화가 가장 적은 안 (architecture-critic이 과잉으로 지적하지 않은 안)
기술 선정요구사항·비기능 요구가 요구하는 것만 추가. 같은 일을 하는 표준·안정 버전 우선(FastAPI + Pydantic v2 + SQLAlchemy 2.x + pytest·httpx). 버전은 설치해 확인한 값으로 고정
작업 순서선행 관계 → 위험 높은 것 먼저 → 의존 적은 것 먼저
규칙 카드·문서와 실제 동작이 다름현재 동작을 계약으로 고정하고 "버그 후보"로 기록 (리팩토링·고도화 중 동작 변경 금지)
리팩토링 우선 도메인·순서위험도 표에서 커버리지가 낮고 변경이 잦은 것 먼저. 동률이면 의존이 적은 것

자동 승인 대상이 아닌 일

자동 승인 모드에서도 다음은 하지 않습니다.
  • 원격 저장소 작업(push, PR), 저장소 밖 파일 수정, 데이터·파일 대량 삭제
  • user 종류 항목(/plugin, /mcp, /ralph-loop 등) — 실행하지 않고 "사용자 실행 필요"를 기록

  • 완료 확인이 실패한 채로 다음 단계로 넘어가기 — 고치지 못하면 그 자리에서 멈추고 보고

12. 완료 확인과 단계 보고서

"끝났다"는 말을 믿지 않고 확인하기 위한 장치입니다. 단계마다 stage-map.json의 checks에 확인 항목이 있고, 모든 단계에는 단계 보고서 확인이 자동으로 붙습니다.

확인 항목의 종류

종류예확인 방법

슬래시 명령(/…)에는 개입하지 않습니다. 훅 스크립트가 실패해도 세션은 막히지 않습니다(오류는 stderr로만 남기고 종료 코드 0).

19. 한계와 주의

  • 호출은 지시로만 합니다. 다른 플러그인은 Claude가 Skill·Agent 도구로 부르도록 지시하는 방식으로 실행합니다. 훅이 직접 실행하지는 않습니다.
  • 완료 확인은 형식을 봅니다. 문서에 필요한 항목과 ID가 있는지, 테스트가 통과하는지는 확인하지만, 설계가 좋은지·요구사항 해석이 맞는지는 판단하지 않습니다. 승인 지점과 결정 기록을 사람이 보는 이유입니다.
  • 다른 워크플로 플러그인과 함께 쓸 때. 트랙 추천은 훅이 넣는 안내라서, 같은 요청을 자기 절차로 처리하라고 강하게 지시하는 플러그인이 함께 켜져 있으면 밀릴 수 있습니다. 요청에 "stage-pilot으로"를 넣거나 프로젝트 단위로 하나만 켭니다.
  • 트랙 추천은 근사치입니다. 파이썬·PHP 파일 수와 키워드로 판단하므로 애매한 요청은 사람이 고릅니다. 레거시 프로젝트에서 트랙 키워드가 없으면 하나로 단정하지 않고 기능 추가·리팩토링·고도화 중 고르라고 안내합니다.
  • PHP 지원 범위. 판별·ID 추적·테스트 실행은 PHP를 지원하지만, 기술 선정 원칙과 일부 추천 플러그인(pyright-lsp, pydantic)은 Python·FastAPI 기준이라 PHP 프로젝트에서는 fallback 기록이 남습니다. 실제 CodeIgniter 저장소 실전 평가는 아직 하지 않았습니다.
  • 설치 여부만 봅니다. 카드의 "미설치"는 설치 목록 기준이며, 설치했지만 꺼 둔 플러그인은 구분하지 않습니다.
  • 자동 승인은 기본 원칙을 따릅니다. 팀의 판단이 기본안과 다른 결정(예: 기능 추가와 함께 기존 API를 바꾸기)은 자동 모드에서 하지 않으므로, 결정 기록을 보고 사람이 이어서 처리합니다.
  • 무거운 단계는 오래 걸립니다. code-modernization의 assess·map·extract-rules·harden, claude-security, subagent-driven-development는 여러 에이전트를 돌려 수십 분이 걸릴 수 있습니다.
  • 리팩토링 트랙의 단계 데이터는 가이드의 사본입니다. 가이드를 고치면 stage-map.json도 함께 고쳐야 하며, 테스트는 문서 앵커가 있는지만 확인합니다.

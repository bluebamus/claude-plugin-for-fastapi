stage-pilot 사용 매뉴얼

stage-pilot은 FastAPI 레거시 고도화 워크플로를 따라가는 동안 "지금 단계에서 어떤 플러그인을 어떤 순서로 쓰고, 어디서 멈춰 확인받아야 하는가"를 알려 주고, 원하면 그 플러그인을 직접 호출해 단계를 수행하는 Claude Code 플러그인입니다.

이 문서는 처음 쓰는 사람이 설치부터 자동 수행까지 혼자 따라 할 수 있도록, 개념 → 설치 → 빠른 시작 → 기능별 설명 → 전체 단계 표 → 문제 해결 순서로 구성했습니다.

1. stage-pilot이란

풀려는 문제

통합 가이드는 레거시 FastAPI 프로젝트를 0~11단계로 나누고, 단계마다 써야 할 플러그인 20여 개와 승인 지점을 정해 두었습니다. 문서는 자세하지만, 실제로 작업할 때는 세 가지가 어렵습니다.

  • 지금 몇 단계인지, 이 단계에서 무엇을 써야 하는지를 매번 문서에서 다시 찾아야 합니다.
  • 플러그인 이름을 알아도 스킬인지, 에이전트인지, 명령인지에 따라 부르는 방법이 다릅니다.
  • 작업에 몰입하다 보면 단계를 건너뛰거나, 확인받아야 할 지점을 지나치기 쉽습니다.

stage-pilot이 하는 일

제안

현재 단계의 주 플러그인·보조 플러그인·조건부 플러그인, 실행 순서, 멈출 곳, 완료 기준을 한 장의 "단계 카드"로 보여 줍니다. 설치되지 않은 플러그인은 설치 명령까지 알려 줍니다.

수행

단계 카드의 실행 순서대로 스킬·에이전트·명령을 실제로 호출해 작업합니다. 기본은 승인 지점에서 멈추고, 자동 승인 모드에서는 가이드의 기본 원칙으로 결정하며 끝까지 진행합니다.

감시

대화 중 요청이 다른 단계의 일이면 "지금은 4단계인데 이 요청은 9단계 일"이라고 짚어 줍니다. 건너뛰기를 막지는 않고, 알고 고르게 합니다.

기록

현재 단계, 거쳐 온 단계, 자동으로 내린 결정과 근거를 프로젝트 안 상태 파일에 남겨, 세션을 다시 열어도 이어서 작업할 수 있습니다.

한눈에 보는 흐름

/stage-pilot:stage init default→ /stage-pilot:stage
단계 카드 확인→ /stage-pilot:stage run
플러그인 호출·작업→ 승인 지점
확인 또는 자동 결정→ /stage-pilot:stage next

2. 먼저 알아 둘 개념

단계 (stage)
워크플로의 한 구간입니다. 통합 가이드 기준으로 pre(진입 전 매뉴얼)와 0~11이 있습니다. 시나리오 가이드에는 4-7처럼 여러 단계를 묶은 id도 있습니다.
프로필 (profile)
어느 가이드의 단계를 따를지 정합니다. default(통합 가이드), fastapi-default(계층 구조가 이미 있는 저장소), g6(테스트 없는 레거시, 슬라이스 반복) 세 가지입니다.
단계 카드
한 단계의 정보를 모은 요약입니다. 주 플러그인, 보조 플러그인, 조건부 플러그인, 실행 순서(run), 승인 지점, 완료 기준, 현재 모드, 미설치 플러그인, 다음 단계가 들어 있습니다.
실행 항목 (run)
단계에서 순서대로 할 일입니다. 종류는 다섯 가지입니다.
종류뜻stage-pilot이 처리하는 방법
skillClaude가 불러와 따르는 작업 지침Skill 도구로 호출 (예: superpowers:test-driven-development)
agent별도 컨텍스트에서 일하는 전문 작업자Agent 도구로 호출 (예: feature-dev:code-explorer), 독립적인 것은 병렬로
command플러그인의 슬래시 명령Skill 도구로 플러그인:명령 이름을 호출 (예: ponytail:ponytail-review)
shell터미널 명령Bash로 실행. 파일을 바꾸는 명령은 제안 모드에서 먼저 보여 줌
user사람만 실행할 수 있는 명령실행하지 않고 그대로 보여 줌 (/plugin, /mcp, /ralph-loop 등)
조건부 실행 항목 (when)
조건이 맞을 때만 하는 실행 항목입니다. 예를 들어 4단계의 dispatching-parallel-agents는 "서로 독립적인 도메인이 2개 이상일 때"만 씁니다. stage-pilot은 프로젝트를 보고 조건을 판정하며, 쓰지 않을 때는 그 근거를 기록합니다.
승인 지점 (approval)
사람이 결정해야 하는 곳입니다. 예: "규칙 카드와 실제 동작이 다를 때 어느 쪽을 계약으로 볼지". 기본 모드에서는 여기서 멈춥니다.
완료 기준 (done)
다음 단계로 넘어가기 전에 실제 출력으로 확인할 조건입니다. 예: "규칙 카드마다 계약 테스트, 전부 통과".
모드
제안 모드(기본): 알려 주기만 합니다. 수행: run을 입력하면 플러그인을 호출해 작업하되 승인 지점에서 멈춥니다. 자동 승인 모드: auto on이면 승인 지점에서 멈추지 않고 정해진 원칙으로 결정하며 끝까지 진행합니다.

3. 설치

준비물

  • Claude Code (CLI, 데스크톱, IDE 확장 중 하나)
  • Node.js — 훅과 상태 스크립트가 Node.js 표준 라이브러리만으로 동작합니다. 별도 npm 패키지는 필요 없습니다.
  • stage-pilot이 호출할 플러그인 — 가이드의 플러그인을 설치해 두어야 수행 모드가 실제로 호출할 수 있습니다. 없어도 제안 모드는 동작하며, 카드에 설치 명령이 나옵니다.

마켓플레이스로 설치 (권장)

/plugin marketplace add bluebamus/claude-plugin-for-fastapi
/plugin install stage-pilot@claude-plugin-for-fastapi

저장소를 클론해 두었다면 GitHub 주소 대신 로컬 경로를 써도 됩니다: /plugin marketplace add C:/work/claude-plugin-for-fastapi

설치 확인

  1. Claude Code에서 /stage-pilot:stage profiles를 입력합니다.
  2. default, fastapi-default, g6 세 줄이 나오면 설치된 것입니다.

4. 10분 시작하기

리팩토링할 FastAPI 프로젝트 폴더에서 Claude Code를 열고 다음 순서로 진행합니다.

  1. 시작 단계 정하기 — 처음이면 진입 전 매뉴얼부터 시작합니다. 
    /stage-pilot:stage init default pre
    프로젝트에 .claude/stage-pilot/state.json이 생기고, 그 단계의 카드가 나옵니다. 이 파일이 있는 프로젝트에서만 stage-pilot의 훅이 동작합니다.
  2. 카드 읽기 — 언제든 현재 단계를 다시 보려면: 
    /stage-pilot:stage
    예시 출력: 
    ■ stage-pilot · 통합 가이드 — 로컬 FastAPI 레거시 고도화 (0~11단계)
현재: 4단계 — 기존 동작 보호 테스트 작성  (docs/default/fastapi-claude-plugins-guide.html#s4)
주 플러그인: superpowers, code-modernization
보조: pr-review-toolkit, ralph-loop
실행 순서:
  1. [Skill] superpowers:test-driven-development
  2. [Agent] code-modernization:test-engineer — 규칙 카드 → 특성화 테스트
  3. [Skill] superpowers:dispatching-parallel-agents (조건: 서로 독립적인 도메인(라우터 묶음)이 2개 이상일 때)
  4. [사용자 입력] /ralph-loop "..." --completion-promise CONTRACT_DONE --max-iterations 15 — 첫 테스트 파일 승인 후에만
승인 지점(STOP): 규칙 카드와 실제 동작이 다를 때 어느 쪽을 계약으로 볼지(원칙: 현재 동작 유지)
완료 기준: 규칙 카드마다 계약 테스트, 전부 통과
모드: 제안 (승인 지점에서 멈춤)
다음: 5단계 — 라우터에서 비즈니스 로직 분리
  3. 단계 수행 — 카드의 실행 순서대로 플러그인을 호출해 작업합니다. 
    /stage-pilot:stage run
    승인 지점에 닿으면 결과를 요약하고 결정할 것을 묻습니다. 답하면 이어서 진행합니다.
  4. 다음 단계로 — 완료 기준을 확인한 뒤: 
    /stage-pilot:stage next
  5. (선택) 자동 승인 — 확인 없이 진행하고 싶은 구간에서: 
    /stage-pilot:stage auto on
/stage-pilot:stage run --through 6
    현재 단계부터 6단계까지 플러그인을 호출해 수행하고, 결정은 모두 기록합니다. 끝나면 auto off로 되돌립니다.
명령을 쓰지 않고 평소처럼 말해도 됩니다. "보호 테스트 써 줘", "지금 뭘 써야 해?" 같은 요청에도 훅이 현재 단계와 추천 플러그인을 Claude에게 알려 주므로, Claude가 카드 기준으로 답합니다.

5. 명령 레퍼런스

슬래시 명령 /stage-pilot:stage

입력하는 일파일 변경
/stage-pilot:stage 또는 status현재 단계 카드를 보여 줌. 미설치 플러그인의 설치 명령을 강조없음
profiles프로필 목록과 각 프로필의 단계 id없음
init <profile> [stage] [--auto]상태 파일을 만들고 시작 단계를 정함. stage를 생략하면 pre. --auto를 주면 자동 승인 모드로 시작상태 파일
goto <stage>현재 프로필에서 지정 단계로 이동. 이전 단계 완료 기준이 확인되지 않았으면 먼저 알림상태 파일
next완료 기준을 확인한 뒤 다음 단계로상태 파일
auto on / auto off자동 승인 모드 켜기·끄기. 켤 때 자동 승인 대상이 아닌 일을 한 줄로 알림상태 파일
run [stage]지정 단계(생략 시 현재 단계)를 플러그인 호출로 수행프로젝트 코드·테스트
run [stage] --through <stage>지정 단계까지 이어서 수행 (자동 승인 모드에서 의미가 있음)프로젝트 코드·테스트

상태 스크립트 stage.js

슬래시 명령과 스킬은 내부적으로 이 스크립트를 부릅니다. 터미널에서 직접 써도 됩니다. 경로는 설치 위치의 plugins/stage-pilot/scripts/stage.js입니다.

node stage.js status                     # 현재 단계 카드
node stage.js profiles                   # 프로필 목록
node stage.js set default 4 [--auto]     # 단계 지정 (기존 결정 기록은 유지)
node stage.js next                       # 다음 단계
node stage.js auto on|off                # 자동 승인 모드
node stage.js log "결정과 근거"           # 결정 기록 추가
node stage.js plan [stage]               # 도구로 호출할 항목(invoke)과 안내만 할 항목(other)을 JSON으로
node stage.js session|prompt             # 훅용 (stdin JSON)
# 모든 명령에 --cwd <프로젝트 경로> 를 붙이면 다른 폴더의 상태를 다룸

6. 제안 모드

기본 모드입니다. stage-pilot은 알려 주기만 하고 아무것도 실행하지 않습니다. 플러그인 사용법을 익히는 중이거나, 각 단계를 직접 손으로 진행하고 싶을 때 씁니다.

이렇게 물어보면 됩니다

요청 예시stage-pilot의 응답
"보호 테스트 단계 하려는데 뭘 써야 해? 실행은 하지 마."주 플러그인 → 보조 → 조건부 순서로 추천하고, 실행 순서와 멈출 곳(승인 지점)을 알려 줌
"지금 바로 보안 검토부터 해도 될까?" (현재 4단계)"현재 4단계이고 보안 검토는 9단계라 단계를 건너뛰게 됩니다"라고 알리고, 9단계의 플러그인과 승인 지점을 함께 보여 줌. 건너뛸지는 사용자가 정함
"pydantic 플러그인 없는데 7단계 할 수 있어?"설치 명령(/plugin marketplace add pydantic/skills 후 /plugin install …)을 안내하고, 설치하지 않으면 어떤 부분을 직접 해야 하는지 알려 줌

조건부 플러그인을 권하는 기준

카드의 "조건부" 줄은 조건이 맞을 때만 권합니다. 예를 들어 context7은 질의가 외부 서버로 나가므로 "문서 조회를 허용할 때만", playwright는 "Jinja 템플릿·관리자 화면이 있을 때만" 권합니다. 조건이 맞는지 애매하면 한 줄로 물어봅니다.

7. 수행 모드

/stage-pilot:stage run을 입력하거나 "4단계 진행해 줘"처럼 분명히 요청하면, 카드의 실행 순서대로 플러그인을 실제로 호출해 작업합니다.

진행 순서

  1. 계획 받기 — stage.js plan으로 도구로 호출할 항목(invoke)과 안내만 할 항목(other)을 나눕니다.
  2. 플러그인 호출 — 스킬·명령은 Skill 도구로, 에이전트는 Agent 도구로 부릅니다. 같은 일을 Claude가 직접 해 버리고 플러그인을 생략하지 않습니다. 가이드가 정한 도구가 실제로 쓰이게 하는 것이 이 플러그인의 목적이기 때문입니다.
  3. 조건 판정 — when이 붙은 항목은 프로젝트를 보고 판정합니다. 조건이 맞지 않으면 호출하지 않고 "조건 불충족: 근거"를 기록합니다.
  4. 대체 수행 — 플러그인이 설치되지 않았거나 프로젝트 스킬(fastapi-layer-slice 등)이 아직 없으면, 같은 목적의 작업을 직접 하고 "대체 수행"으로 기록합니다. 프로젝트 스킬을 만들 단계도 알려 줍니다.
  5. 결과 반영 — 리뷰·분석 에이전트가 고칠 거리를 내면, 그 단계의 목표 범위 안에서 실제로 고칩니다. 리뷰 지적은 superpowers:receiving-code-review 기준으로 검증한 뒤 반영합니다.
  6. 승인 지점 — 결과를 요약하고 결정할 것을 묻고 멈춥니다(자동 승인 모드가 아닐 때).
  7. 완료 확인 — 완료 기준을 테스트 결과·산출물 경로 같은 실제 출력으로 확인하고, 다음 단계로 갈지 묻습니다.

수행 후 보고 형식

■ 10단계 수행 결과
호출한 플러그인: code-simplifier:code-simplifier → 중복 계산 함수 1개로 통합
                ponytail:ponytail-review → 쓰지 않는 옵션 2개 보고
                pr-review-toolkit:code-reviewer → 지적 3건 (2건 반영, 1건 반박)
변경: main.py, tests/test_smoke.py
완료 기준: pytest 3 passed — 충족

수행 모드에서도 하지 않는 일

  • 원격 저장소 작업(push, PR). 11단계의 finishing-a-development-branch는 1번(로컬 병합)만 씁니다.
  • user 종류 항목의 실행 — /ralph-loop, /plugin, /mcp는 사람이 입력합니다.
  • g6 프로필에서 저장소 안에서 code-modernization 명령 실행 — 저장소 밖 분석 작업 공간(~/work/g6-analysis)에서만 실행합니다.

8. 자동 승인 모드

자동 승인 모드에서는 승인 지점에서 멈추지 않습니다. 가이드가 정한 기본안으로 결정하고, 그 결정과 근거를 상태 파일에 남긴 뒤 계속 진행합니다. 반복적인 단계를 빠르게 지나가거나, 밤새 여러 단계를 진행해 두고 아침에 결정 기록을 검토하는 식으로 쓸 수 있습니다.

/stage-pilot:stage auto on          # 켜기
/stage-pilot:stage run --through 8  # 현재 단계부터 8단계까지 연속 수행
/stage-pilot:stage auto off         # 끄기

처음부터 자동으로 시작하려면 /stage-pilot:stage init default 3 --auto처럼 --auto를 붙입니다. 자동 모드는 next나 goto로 단계를 옮겨도 유지됩니다.

자동 결정 원칙

승인 지점마다 사람이 고를 내용을 아래 원칙으로 대신 고릅니다. 원칙은 모두 "동작을 바꾸지 않는 쪽, 범위를 좁히는 쪽"입니다. 리팩토링 중에 의도치 않은 변화가 생기는 것을 막기 위해서입니다.

결정할 일자동으로 고르는 것
규칙 카드와 실제 동작이 다름현재 동작을 계약으로 고정하고 "버그 후보"로 기록 (리팩토링 중 동작 변경 금지)
리팩토링 우선 도메인·순서위험도 표에서 커버리지가 낮고 변경이 잦은 것 먼저. 동률이면 의존이 적은 것
설계안 선택기존 구조와 차이가 가장 작은 안 (architecture-critic이 과잉 설계로 지적하지 않은 안)
응답 필드·입력 허용 범위가 바뀌는 수정하지 않음. API 계약 변경은 별도 작업으로 기록
보안 발견두 도구가 함께 찾았거나 근거 코드가 명확한 것만 수정, 나머지는 기록
남은 리뷰 이슈이번 단계 범위 안이면 수정, 밖이면 기록
커밋로컬 커밋만, 단계·논리 단위로

자동 승인 대상이 아닌 일

자동 승인 모드에서도 다음은 하지 않습니다.
  • 원격 저장소 작업(push, PR), 저장소 밖 파일 수정, 데이터·파일 대량 삭제
  • user 종류 항목(/plugin, /mcp, /ralph-loop 등) — 실행하지 않고 "사용자 실행 필요"를 기록
  • 테스트가 실패한 채로 다음 단계로 넘어가기 — 고치지 못하면 그 자리에서 멈추고 보고

결정 기록 읽기

자동으로 내린 결정은 상태 파일의 decisions에 쌓입니다. 아래는 실제 평가에서 3단계를 자동 수행했을 때 남은 기록입니다.

"decisions": [
  { "stage": "3", "text": "리팩토링 순서 확정: 1) POST /appointments (커버리지 낮음, 금액 규칙이 라우터 안에 있어 위험 높음) 2) GET /appointments/{id} — 근거: 커버리지 낮고 위험 높은 것 먼저", "auto": true },
  { "stage": "3", "text": "제외 엔드포인트: 없음 — 두 개뿐이고 둘 다 핵심 경로", "auto": true },
  { "stage": "3", "text": "버그 후보 기록(수정 안 함): 음수/0 slots 허용 → 4단계에서 현재 동작으로 고정", "auto": true }
]

기록에서 확인할 것은 세 가지입니다.

  • "대체 수행" — 플러그인이 없어 직접 한 일입니다. 해당 플러그인을 설치하고 다시 돌릴지 판단합니다.
  • "조건 불충족" — 조건부 항목을 건너뛴 근거입니다. 근거가 맞는지 봅니다.
  • "버그 후보", "별도 작업" — 리팩토링 범위 밖으로 미룬 일입니다. 다음 작업 목록으로 옮깁니다.

9. 훅이 하는 일

stage-pilot에는 훅이 두 개 있습니다. 둘 다 상태 파일이 있는 프로젝트에서만 동작하므로, 다른 프로젝트에서는 아무 영향이 없습니다.

훅언제하는 일
SessionStart세션 시작·재개·/clear·압축 직후현재 단계 카드와 현재 모드의 행동 규칙을 Claude의 컨텍스트에 넣음. 세션을 새로 열어도 단계를 이어 갈 수 있는 이유
UserPromptSubmit요청을 보낼 때마다요청 문장을 단계별 키워드와 대조해, 다른 단계의 일이면 "이 요청은 N단계 성격, 현재는 M단계"와 추천 플러그인을 알림. 슬래시 명령(/…)에는 개입하지 않음

훅 스크립트가 실패해도 세션은 막히지 않습니다(오류는 stderr로만 남기고 종료 코드 0).

12. 고치고 늘리기

단계 정보를 바꾸려면

모든 단계 정보는 plugins/stage-pilot/skills/stage-pilot/references/stage-map.json 한 파일에 있습니다. 가이드 문서를 고쳤다면 이 파일도 함께 고칩니다. 한 단계는 다음 필드로 이루어집니다.

{
  "id": "4", "title": "기존 동작 보호 테스트 작성", "anchor": "#s4",
  "primary": ["superpowers", "code-modernization"],      // plugins 목록의 이름
  "assist": ["pr-review-toolkit", "ralph-loop"],
  "conditional": [{ "plugin": "serena", "when": "대량 심볼 이동" }],
  "run": [
    { "type": "skill", "ref": "superpowers:test-driven-development" },
    { "type": "agent", "ref": "code-modernization:test-engineer", "note": "규칙 카드 → 특성화 테스트" },
    { "type": "skill", "ref": "superpowers:dispatching-parallel-agents", "when": "서로 독립적인 도메인이 2개 이상일 때" }
  ],
  "approval": "…", "done": "…", "keywords": ["보호 테스트", "특성화"]
}
  • keywords는 훅이 요청 문장에서 단계를 알아보는 데 씁니다. 팀이 자주 쓰는 표현을 넣으면 감지가 정확해집니다.
  • 새 플러그인을 쓰려면 먼저 상단 plugins에 설치 ID와 역할을 등록합니다.

바꾼 뒤 확인

node --test plugins/stage-pilot/tests/stage.test.js

데이터 정합성(모든 플러그인이 목록에 있는지, 단계 id 중복), 가이드 문서의 앵커가 실제로 있는지, 훅 출력, 자동 모드·결정 기록을 확인합니다.

실제 Claude Code로 평가하려면

python eval/run_eval.py --iters 1,2,3 --out <.claude가 없는 폴더> --python <fastapi·pytest가 설치된 python>

회차마다 복잡도가 다른 가상 레거시를 만들고, 제안·단계 건너뛰기 감지·자동 수행을 실제로 돌려 채점합니다. 자세한 내용은 13. 검증 결과에 있습니다.

13. 검증 결과

stage-pilot이 실제로 플러그인을 제안·호출하는지 확인하기 위해, 회차마다 복잡도와 도메인이 다른 가상 FastAPI 레거시 프로젝트를 만들고 실제 Claude Code에서 세 과제를 돌렸습니다. 채점은 Claude의 답변 문구가 아니라 실제 도구 호출 기록(stream-json)과 프로젝트 상태(파일 변경, 테스트, 커밋, 상태 파일)로 했습니다.

최종본 결과: 7회 중 7회 통과, 연속 7회 — 목표(같은 기준으로 5회 이상 연속 통과)를 달성했습니다.

평가 방법

과제무엇을 확인하나
제안그 단계의 주 플러그인을 모두 언급하고 승인 지점을 안내하는가. 파일을 고치거나 run 항목을 호출하지 않는가
단계 건너뛰기 감지다른 단계 요청에 현재 단계와 요청 단계 번호를 모두 밝히는가
자동 수행auto on 상태에서 run(또는 run --through)이 호출 가능한 run 항목을 모두 실제로 호출하는가, 질문 없이 결정을 기록하는가, 수행 후 테스트가 통과하는가, 리팩토링 단계는 코드를 실제로 바꾸는가, 11단계는 로컬 커밋으로 작업 트리를 정리하고 원격 작업을 하지 않는가
복잡도가상 레거시의 특징
L1main.py 한 파일, 메모리 저장소, 라우터 안 비즈니스 규칙
L2+ sqlite3 원시 SQL 문자열 조립(SQL 인젝션), 라우터에서 직접 커밋
L3+ app 패키지, async 라우터 안의 동기 SQLAlchemy 세션과 time.sleep, 의존성 주입 없음
L4+ 도메인 2개, 요청 하나에 커밋 2번, Pydantic v1식 orm_mode, 비밀값 하드코딩, Jinja 관리자 화면
L5+ 도메인 3개, 도메인 간 라우터 직접 import, async 안의 requests, BackgroundTasks

도메인은 쇼핑몰(주문), 도서관(대출), 병원(예약), 호텔(숙박), 학교(수강) 5종이며 회차마다 조합이 바뀝니다. 공식 플러그인은 --plugin-dir로 실행할 때만 불러왔고, pyright-lsp는 언어 서버가 없는 환경이라 제외했습니다.

관찰한 동작

  • 조건 판정: 도메인이 하나인 프로젝트(2·11회차)에서는 병렬 에이전트를 부르지 않고 "조건 불충족: superpowers:dispatching-parallel-agents — 도메인 1개(orders 라우터만 존재)"처럼 근거를 기록했습니다. 조건부 플러그인도 같은 방식으로 판정했습니다. 예: "plugin-dev — async def가 없음", "serena — 이동 심볼 3개, 대량 이동 아님", "context7 — 외부 문서 조회 허용 없음". 여러 도메인 프로젝트에서 4단계를 자동 수행한 회차는 없어, 조건이 충족될 때의 호출은 이번 평가에서 확인하지 않았습니다.
  • 대체 수행: pydantic 플러그인이 없는 환경(7·16회차)에서는 스키마 분리를 직접 하고 "대체 수행"으로 기록했습니다. 프로젝트 스킬 fastapi-layer-slice가 없을 때(6·13회차)는 같은 목적의 분리를 직접 했습니다. 13회차에서는 5단계에서 skill-creator로 스킬을 만들었지만 .claude/skills 쓰기가 권한으로 거부되어, 초안을 docs/skills/에 두고 그 절차대로 6단계를 직접 수행했습니다(문제 해결 참고).
  • 자동 결정: 3단계에서는 "커버리지 낮고 위험 높은 엔드포인트 먼저"로 순서를 정하고, 음수 입력 허용 같은 동작은 고치지 않고 "버그 후보"로 남겼습니다(동작 유지 원칙).
  • 하지 않은 일: 모든 회차에서 원격 저장소 작업과 AskUserQuestion 질문이 없었습니다. 변경이 없을 때는 빈 커밋을 만들지 않았습니다.

전체 회차 기록과 2차 결과는 저장소의 eval/RESULTS.md에 있습니다.

14. 문제 해결

증상원인해결
훅이 아무것도 알려 주지 않음그 프로젝트에 상태 파일이 없음/stage-pilot:stage init default로 시작
설치했는데 카드에 "미설치"로 나옴--plugin-dir로 불러온 플러그인은 설치 목록에 없어서 카드가 알지 못함무시해도 됩니다. 수행 모드는 Claude가 실제로 쓸 수 있는 도구 목록을 기준으로 호출합니다
설치했는데 수행 모드가 "대체 수행"을 함플러그인이 설치는 됐지만 비활성화됨, 또는 세션을 다시 열지 않음/plugin에서 활성화 확인 후 세션 재시작
자동 모드인데 파일 편집 때마다 권한을 물음프로젝트가 ~/.claude 아래처럼 Claude Code가 민감 경로로 보는 곳에 있음프로젝트를 일반 작업 폴더로 옮김. 권한 모드가 편집을 허용하는지 확인 (acceptEdits 등)
skill-creator로 만든 프로젝트 스킬이 .claude/skills에 저장되지 않음Claude Code는 프로젝트의 .claude/ 폴더 쓰기를 민감 작업으로 보고 확인을 요구함. 비대화형 실행(claude -p)에서는 거부됨대화형 세션에서 쓰기를 승인하거나, 초안(stage-pilot은 이때 docs/skills/에 둠)을 직접 .claude/skills/로 옮김
자동 모드인데 중간에 멈춤테스트가 실패했고 고치지 못함 (의도된 멈춤)보고된 실패를 확인하고 고친 뒤 run을 다시 입력
Windows에서 훅 테스트 시 빈 출력Git Bash의 /tmp/… 경로를 JSON에 넣으면 Node.js가 다른 경로로 해석JSON에는 C:/… 형식 경로 사용 (실제 Claude Code는 Windows 경로를 넘김)
요청한 단계를 다르게 알아봄키워드 대조는 근사치상태 파일의 단계가 기준입니다. 자주 틀리면 keywords를 보강

15. 한계와 주의

  • 호출은 지시로만 합니다. 다른 플러그인은 Claude가 Skill·Agent 도구로 부르도록 지시하는 방식으로 실행합니다. 훅이 직접 실행하지는 않습니다.
  • 설치 여부만 봅니다. 카드의 "미설치"는 설치 목록 기준이며, 설치했지만 꺼 둔 플러그인은 구분하지 않습니다.
  • 단계 감지는 근사치입니다. 키워드 대조라 짧거나 모호한 요청은 감지하지 못할 수 있습니다.
  • 자동 승인은 가이드의 기본안을 따릅니다. 팀의 판단이 기본안과 다른 결정(예: 계약 변경을 이번에 함께 하기)은 자동 모드에서 하지 않으므로, 결정 기록을 보고 사람이 이어서 처리합니다.
  • 무거운 단계는 오래 걸립니다. code-modernization의 assess·map·harden, claude-security는 여러 에이전트를 돌려 수십 분이 걸릴 수 있습니다.
  • 단계 데이터는 사본입니다. 가이드를 고치면 stage-map.json도 함께 고쳐야 하며, 테스트는 문서 앵커가 있는지만 확인합니다.

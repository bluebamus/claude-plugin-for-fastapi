gnuboard/g6 분석·설계·리팩토링 가이드

g6는 그누보드5를 FastAPI로 옮긴 CMS로, 서버 렌더링 화면·관리자·REST API·플러그인이 한 앱에 있습니다. 테스트는 0건이고, 동기 DB 세션을 async def에서 쓰며, 한 요청의 커밋이 서비스·라이브러리·미들웨어에 흩어져 있습니다. 전략은 테스트로 현재 동작을 먼저 고정한 뒤, 도메인 하나씩(슬라이스) fastapi-default-project-structure의 계층 규칙으로 옮기는 점진적 고도화입니다. 동기 세션·Jinja 템플릿·기존 URL은 유지합니다.

두 저장소를 언제·어떻게 쓰나

g6는 옮겨 갈 대상, fastapi-default-project-structure는 따라갈 모양입니다. g6의 0~5단계(실행·분석·테스트 고정)는 기준 구조 없이도 진행할 수 있지만, 6단계(슬라이스 설계)부터는 기준 구조 문서의 3·8·11단계 산출물이 필요합니다.

기준 구조에서 가져오는 것가져오지 않는 것 (지금은)
  • 계층 책임 표: View(어댑터) → Service(유스케이스) → Repository(쿼리) → Session
  • 트랜잭션 규칙: 쓰기 핸들러가 응답 준비 뒤 커밋 1회, Repository·라이브러리는 커밋하지 않음
  • 층별 테스트 모양: 가짜 Repository 서비스 단위 테스트, SQLite Repository 테스트, 기능 통합 테스트
  • 설정 검사 아이디어: 예시 비밀값("secretkey" 등)이면 기동 거부
  • layered-slice 스킬(문서1 11단계)과 CLAUDE.md 규칙
  • AsyncSession·aiomysql 전환 — 146곳의 커밋 지점과 24곳의 자체 세션을 정리하기 전에는 위험이 큼
  • Redis 필수 기동·Celery — g6는 APScheduler를 씀
  • JWT 회전·레이트 리밋 구현 전체 — 보안 단계에서 필요한 것만 선별
  • 디렉터리 전면 재배치(app/features/*) — URL·템플릿·플러그인이 기존 경로에 묶여 있음

플러그인 구성

각 플러그인이 무엇인지, 어떤 목적으로, 어떻게 쓰는지, g6에서의 실제 시나리오로 정리했습니다. 채택·조건부·제외 판정은 통합 플러그인 가이드의 확장 플러그인 검토(신뢰성·안정성 6개 기준)를 따르고, g6의 조건(테스트 0건, 화면 중심, 슬라이스 반복)에 맞춰 쓰임을 정했습니다.

g6의 플러그인 전략 한 줄 요약 — 테스트 없는 레거시이므로 code-modernization의 진단·규칙 카드 기능을 끝까지 쓰고(/modernize-review·/modernize-status·/modernize-harden·version-delta-analyst 포함), 화면이 핵심이라 playwright는 조건이 충족돼 채택하며(버전 고정), 슬라이스를 여러 번 반복하므로 skill-creator로 절차를 고정·평가합니다. 기계적 반복만 ralph-loop에 맡깁니다.

code-modernization 리팩토링 — g6의 주 도구

무엇: 레거시를 "진단 → 계획 승인 → 변환 → 동등성 증명" 순서로 다루는 명령(/modernize-preflight, -assess, -map, -extract-rules, -brief, -transform, -harden)과 에이전트(legacy-analyst, business-rules-extractor, test-engineer, architecture-critic). 목적: g6처럼 테스트 없는 레거시의 구조 지도와 업무 규칙 목록을 만드는 데 가장 잘 맞습니다. 사용법: 저장소 밖 분석 작업 공간(~/work/g6-analysis)에서 /modernize-preflight g6 --source ~/work/g6로 링크를 만들고 명령에 g6를 넘깁니다(0단계). 제자리 리팩토링이므로 transform(별도 modernized/에 새 코드 생성)보다 진단 명령과 에이전트 위주로 씁니다. 같은 플러그인의 미활용 기능도 g6에서 가치가 큽니다 — /modernize-review(신뢰도 낮은 규칙 카드 판정 기록), /modernize-status(슬라이스마다 세션 재개 시 산출물 신선도), /modernize-harden(13단계 2차 보안 의견), version-delta-analyst(0단계 FastAPI·Starlette 고정, 로드맵 8 의존성 현대화).

새 계층에서는 커밋·자체 세션·Request 사용을 하지 않습니다. 세션은 주입받고, 커밋은 어댑터가 한 번만 합니다.

g6는 GitHub에서 클론했으므로 origin이 살아 있습니다. 원격 명령 차단 규칙을 처음부터 block으로 둡니다(오탐 범위가 좁음).

---
name: block-remote-git
enabled: true
event: bash
action: block
pattern: git\s+(push|pull|fetch|remote\s+add)|gh\s+pr
---
이 작업은 로컬 전용입니다. 원격 저장소 명령은 실행하지 않습니다.

commit-commands 로컬 커밋

/commit만 씁니다(/commit-push-pr은 원격·gh 필요). g6 커밋 관례는 [fix] 설문조사 > 잘못된 인자 전달 수정처럼 [유형] 영역 > 설명입니다. 이 관례를 유지할지, 기준 구조의 type(scope): 설명으로 바꿀지는 0단계에서 정합니다.

pydantic 확장 · 채택 · 스키마 작성 기준

무엇: Pydantic 팀이 관리하는 스킬 플러그인(pydantic@pydantic-skills, MIT). 제약·필드 메타데이터, 검증기, 판별 유니언, 모델 상속의 권장 작성법을 담고 있고, "애플리케이션 내부 클래스까지 Pydantic으로 만들지 말라"는 지침이 있습니다. 목적: 11단계 입력 DTO 통일에서 API WriteModel(extra="allow")의 필드를 명시할 때의 작성 기준, 그리고 유스케이스가 받는 명령 객체를 Pydantic이 아닌 dataclass로 두는 판단 근거(7단계 Writer와 같은 방식). 주의: v1→v2 이관 절차는 다루지 않습니다 — 그 일은 로드맵 8의 version-delta-analyst·/modernize-uplift가 맡습니다(상세).

ralph-loop 확장 · 범위 한정

무엇: Stop 훅이 종료를 가로채 같은 프롬프트를 반복 주입하는 루프(/ralph-loop, --max-iterations, --completion-promise, 중단 /cancel-ralph, jq 필요). 목적: 완료 조건이 기계적으로 판정되는 반복만 — 3단계 순수 함수 단위 테스트 채우기, 14단계 새 계층 파일의 ruff·pyright 오류 0. 주의: --max-iterations 필수(기본 무제한). 슬라이스 설계·트랜잭션 단일화(동작 변경)·보안 패치에는 쓰지 않습니다. hookify의 "pytest 없이 종료 차단" 규칙과 Stop 훅이 겹치므로 루프 중에는 그 규칙을 warn으로 둡니다(상세).

ponytail 확장 · 범위 한정

무엇: 개인이 별도 마켓플레이스로 배포하는 플러그인(MIT). code-modernization 분석 작업 공간

g6는 코드가 저장소 최상위에 있어, 저장소 안에 legacy/g6 링크를 만들면 저장소가 자기 자신을 가리키는 순환이 생기고 링크가 git 변경으로 잡힙니다. 그래서 code-modernization 명령만 저장소 밖 분석 작업 공간에서 실행합니다. 소스는 읽기만 하므로 리팩토링 세션(저장소)과 충돌하지 않습니다.

# service/errors.py
class PostWriteDenied(Exception):
    def __init__(self, message: str, status_code: int = 400) -> None:
        super().__init__(message)
        self.status_code = status_code


# service/board/post_write_service.py
from dataclasses import dataclass

from service.errors import PostWriteDenied


@dataclass(frozen=True)
class Writer:
    member_id: str          # 비회원이면 ""
    level: int
    client_ip: str
    is_admin: bool


class PostWriteService:
    def __init__(self, boards, writes, points) -> None:
        self.boards = boards
        self.writes = writes
        self.points = points

    def create(self, bo_table: str, command, writer: Writer):
        board = self.boards.get(bo_table)
        if not writer.is_admin and writer.level < board.bo_write_level:
            raise PostWriteDenied("글을 작성할 권한이 없습니다.", 403)
        if not writer.member_id and not command.wr_password:
            raise PostWriteDenied("비회원 글쓰기시 비밀번호를 기재해야 합니다.", 400)

        write = self.writes.add(bo_table, command, writer)
        self.boards.increase_write_count(board)
        if writer.member_id:
            self.points.add_write_point(writer.member_id, board, write)
        return write

from types import SimpleNamespace

import pytest

from service.board.post_write_service import PostWriteService, Writer
from service.errors import PostWriteDenied


class FakeBoards:
    def __init__(self, write_level=1):
        self.board = SimpleNamespace(bo_table="free", bo_write_level=write_level, bo_count_write=0)

    def get(self, bo_table):
        return self.board

    def increase_write_count(self, board):

class FakeWrites:
    def __init__(self):
        self.saved = []

    def add(self, bo_table, command, writer):
        write = SimpleNamespace(wr_id=len(self.saved) + 1, subject=command.wr_subject)
        self.saved.append(write)
        return write


class FakePoints:
    def __init__(self):
        self.calls = []

    def add_write_point(self, member_id, board, write):
        self.calls.append((member_id, write.wr_id))


COMMAND = SimpleNamespace(wr_subject="제목", wr_content="내용", wr_password="")


def writer(member_id="user1", level=2, is_admin=False):

    with pytest.raises(PostWriteDenied) as error:
        service.create("free", COMMAND, writer(level=2))

10단계. async 경계 정리

목표

동기 DB 작업이 이벤트 루프를 막지 않게 합니다. AsyncSession으로 바꾸지 않고 FastAPI의 기본 동작을 이용합니다.

핸들러 상황가장 단순한 처리
안에 await가 없음 (API 글쓰기 등)async def → def. FastAPI가 스레드풀에서 실행
await가 필요함 (화면 글쓰기의 캡차 검증 등)async def 유지, 동기 DB 묶음(유스케이스 호출 + 커밋)을 await run_in_threadpool(...)으로 감쌈
미들웨어 main_middleware이번 슬라이스에서는 손대지 않음 (16단계 후순위 슬라이스)
프롬프트
게시글 작성 API 핸들러를 def 로 바꾸고, 화면 핸들러는 캡차 await 뒤의 동기 DB 묶음을
fastapi.concurrency.run_in_threadpool 로 감싸줘. 세션을 여러 스레드에서 동시에 쓰지 않는지 확인하고,
특성화·통합 테스트를 다시 돌려줘.
실패 대응

의존성 함수가 async라서 문제가 생기면 핸들러만 바꾸고 의존성은 그대로 둡니다. 부하에서의 효과는 측정 전까지 추정이므로, 필요하면 로컬에서 동시 요청 몇십 개로 응답 시간을 비교합니다.

확장 적용(조건부) — plugin-dev·context7

슬라이스가 늘수록 "async def 안에서 동기 세션을 간접 호출" 같은 회귀가 hookify 정규식으로 잡히지 않으면, plugin-dev의 hook-development 스킬로 새 계층·어댑터 경로에만 PostToolUse 프롬프트 훅(처음엔 경고만)을 만듭니다. 편집마다 모델 호출 비용이 생기므로 대상 경로를 좁힙니다. run_in_threadpool 동작을 현재 문서로 확인해야 하면 context7을 씁니다(질의 외부 전송).

fastapi-default-project-structure 분석·설계·고도화 가이드

이 저장소는 이미 View → Dependency → Service → Repository → AsyncSession 계층, 명시적 트랜잭션 규칙, 1,000건이 넘는 테스트를 갖춘 기준 구조입니다. 따라서 할 일은 구조를 다시 쓰는 것이 아니라 ① 흐름을 정확히 이해하고, ② 남은 약점을 작은 단위로 고치고, ③ 새 기능을 같은 절차로 추가하는 방법을 고정하고, ④ 그 패턴을 gnuboard/g6 리팩토링의 목표 설계로 넘기는 것입니다.

이 저장소를 언제·어떻게 쓰나

두 저장소는 역할이 다릅니다. fastapi-default-project-structure는 "따라갈 모양"이고, g6는 "옮겨 갈 대상"입니다. 이 문서의 작업(1~11단계)을 먼저 끝내 기준을 확정한 뒤, g6 문서의 3단계(설계)부터 이 저장소의 패턴을 가져다 씁니다.

from decimal import Decimal

import pytest

from app.features.catalog.exceptions import ProductNotFoundException
from app.features.catalog.models.models import Product
from app.features.catalog.schemas.catalog_schema import ProductUpdate
from app.features.catalog.services.catalog_service import CatalogService


class FakeProductRepository:
    def __init__(self, products=()):
        self.products = {p.id: p for p in products}
        self.update_calls = []

    async def get_by_id(self, product_id):
        return self.products.get(product_id)

    async def update_by_id(self, product_id, changes):
        self.update_calls.append((product_id, changes))
        return None

    async def delete_by_id(self, product_id):
        return self.products.pop(product_id, None) is not None


def make_service(*products):
    repository = FakeProductRepository(products)
    return CatalogService(db_session=None, repository=repository), repository


async def test_update_without_changes_returns_existing_and_sends_no_update():
    existing = Product(id="p1", name="키보드", price=Decimal("10.00"), is_active=True)
    service, repository = make_service(existing)

    result = await service.update_product("p1", ProductUpdate())

    assert result is existing
    assert repository.update_calls == []

    with pytest.raises(ProductNotFoundException):
        await service.get_product("missing")
검증함: 4단계의 생성자 변경을 적용한 임시 사본에서 위 테스트 3건과 기존 catalog 테스트가 함께 통과했습니다(20 passed). 검증 후 사본은 원래대로 되돌렸습니다.

규칙: 테스트 하나는 한 가지 동작만 확인하고, 이름이 곧 명세가 되게 씁니다. 가짜 객체는 테스트에 필요한 메서드만 갖고, mock 라이브러리보다 짧은 클래스가 읽기 쉬우면 클래스를 씁니다.

무엇: claude-code-setup은 저장소를 읽고 훅·스킬·서브에이전트를 추천(읽기 전용), hookify는 마크다운 규칙 파일로 경고·차단 훅을 만듭니다. 목적: 이 저장소의 금지 규칙(Repository·Dependency 커밋 금지, 요청 경로 동기 I/O 금지, config.py 밖 환경 변수 읽기 금지)을 편집 순간에 알려 줍니다.

---
name: no-commit-outside-view
enabled: true
event: file
action: warn
conditions:
  - field: file_path
    operator: regex_match
    pattern: app/features/.*/(repositories|dependencies)/.*\.py$
  - field: new_text
    operator: regex_match
    pattern: \.commit\(\)
---
Repository·Dependency에서는 커밋하지 않습니다. 쓰기 View 본문에서 응답 DTO 검증 뒤 service.commit()을 한 번 호출하세요.

이 저장소는 GitHub에서 클론했으므로 origin이 살아 있습니다. 로컬 전용 원칙을 지키도록 원격 명령 차단 규칙을 처음부터 block으로 둡니다(오탐 범위가 좁음).

---
name: block-remote-git
enabled: true
event: bash
action: block
pattern: git\s+(push|pull|fetch|remote\s+add)|gh\s+pr
---
이 작업은 로컬 전용입니다. 원격 저장소 명령은 실행하지 않습니다.

10단계. 커밋

커밋 원칙: 2~9단계는 단계가 끝날 때마다 커밋합니다(4단계 확대는 기능 하나당 하나). 이 단계는 일괄 커밋이 아니라 아직 커밋하지 않은 변경 정리와 이력 점검입니다.

refactor/baseline 이후 커밋 목록(git log --oneline)과 아직 커밋하지 않은 변경을 보여줘.
아래 기대 이력과 대조해 빠진 커밋, 한 커밋에 관심사가 섞인 곳, 관례 "type(scope): 한글 설명 (그룹)"에 어긋난 메시지를 찾아줘.
기대 이력: test(catalog) 서비스 단위 테스트 → refactor(catalog) 선택적 repository 주입 → 기능별 확대
→ build(coverage) omit 정정 → (선택) refactor(config)·refactor(main) → feat(inventory) → fix(security)·style 정리
남은 변경만 묶음으로 나눠 보여주고, 승인한 묶음만 git add 후 /commit. 커밋마다 테스트 통과 확인.
이미 만든 커밋을 고쳐야 하면 방법(reword·squash)만 제안하고 실행 전에 확인받아줘.

원격 push는 하지 않습니다(block-remote-git 훅이 막음). 문제 시 git revert 또는 아직 공유 전이면 git reset --soft HEAD~1(사용자 확인 후).

작업 브랜치 마무리

커밋을 나눈 뒤 superpowers finishing-a-development-branch로 테스트 통과를 다시 확인하고, 선택지 중 1번 "Merge back to base-branch locally"만 골라 refactor/baseline을 로컬 기준 브랜치로 병합합니다. 2번(push·PR)은 쓰지 않습니다.

로컬 FastAPI 레거시 고도화를 위한 Claude Code 플러그인 가이드

로컬 FastAPI 레거시는 pyright-lsp로 정확히 읽고 → feature-dev·code-modernization으로 흐름과 위험을 파악하고 → superpowers TDD로 보호 테스트를 깐 뒤 → 작은 단위로 레이어를 분리하고 → 보안·단순화·리뷰로 검증하고 → commit-commands로 논리 단위 커밋하는 순서로 고도화합니다. 모든 플러그인은 로컬 파일과 로컬 git만 사용하며, GitHub 연동 기능(/commit-push-pr 등)은 쓰지 않습니다.

기본 구성 13개에 더해, 신뢰성·안정성 기준으로 검토한 확장 플러그인 중 skill-creator(반복 절차를 스킬로 고정)와 pydantic(스키마 작성 기준)을 채택하고, ralph-loop는 완료 조건이 기계적으로 판정되는 반복 작업에만, ponytail은 변경분의 과설계 점검에만 씁니다. 나머지 6개는 조건이 맞을 때만 씁니다. 새로 설치하기 전에, 이미 선정한 플러그인 안에 있지만 쓰지 않던 기능(/modernize-review, /modernize-harden, receiving-code-review 등)부터 씁니다.

개요

전제와 원칙

  • 대상: 로컬에 있는 FastAPI 프로젝트와 로컬 git 저장소 (원격 없음)
  • 불변 조건: 기존 기능과 API 계약(경로, 메서드, 상태 코드, 요청·응답 JSON 형태)을 바꾸지 않음
  • 진행 방식: 대규모 재작성 대신 "테스트로 고정 → 한 가지 책임만 이동 → 테스트 통과 → 커밋"을 반복
  • 현재 문제 가정: 라우터에 비즈니스 로직과 DB 접근이 섞임, 테스트 부족, 책임 경계 불명확, async 함수 안의 동기 블로킹 호출

목표 구조 (FastAPI 실무 레이어드)

app/
├── main.py                # 앱 생성, 라우터 등록, 미들웨어
├── core/                  # 설정(Settings), 보안 유틸, 로깅
├── api/
│   ├── deps.py            # Depends: DB 세션, 현재 사용자, 서비스 조립
│   └── v1/routers/        # HTTP 관심사만: 입력 검증, 상태 코드, 응답 변환
├── schemas/               # Pydantic request/response 모델 (API 계약)
├── services/              # 비즈니스 규칙, 트랜잭션 경계
├── repositories/          # DB 접근만 (쿼리, ORM 매핑)
├── models/                # ORM 엔티티
└── tests/
    ├── contract/          # API 계약 보호 테스트 (httpx AsyncClient)
    ├── services/          # 서비스 단위 테스트 (가짜 repository)
    └── repositories/      # DB 통합 테스트

의존 방향은 routers → services → repositories → models 한 방향입니다. 라우터는 repository를 직접 부르지 않고, 서비스는 FastAPI의 Request·HTTPException을 알지 않으며, 스키마(Pydantic)와 ORM 모델은 분리합니다. 이 규칙은 CLAUDE.md에 기록해 리뷰 플러그인들의 판단 기준으로 씁니다.

이 문서의 대화·출력 예시는 동작을 설명하기 위해 만든 가상 예시입니다. 실제 출력 형식은 버전과 프로젝트에 따라 다릅니다.

pyright-lsp Python 코드 인텔리전스

핵심 역할

Claude가 grep 같은 텍스트 검색 대신 IDE처럼 Python 코드를 심볼 단위로 읽고, 자기가 만든 타입 오류를 빌드 없이 즉시 알아차리게 합니다. 모든 단계의 정확도를 받치는 기반입니다.

내부 동작 방식
  • 플러그인은 pyright-langserver 실행 명령과 .py 확장자 매핑만 Claude Code에 등록합니다. 언어 서버 바이너리는 로컬에 설치돼 있어야 합니다.
  • Claude가 .py 파일을 처음 편집할 때 서버가 시작되고, 이후 두 기능이 켜집니다.
    • 편집 후 자동 진단: 파일을 수정할 때마다 서버가 보고한 타입 오류, 누락 import, 문법 오류를 Claude가 받습니다. 대화에는 Found N new diagnostic issues in M files로 표시되고 Ctrl+O로 상세를 봅니다.
    • LSP 도구 (읽기 전용): 정의로 이동, 모든 참조 찾기, 위치별 타입 정보, 파일 심볼 목록, 워크스페이스 심볼 검색, 구현체 찾기, 호출 계층 추적.
Claude Code와의 상호작용 방식

명령이 없습니다. Claude가 필요할 때 LSP 도구를 스스로 고르고, 진단은 편집마다 자동으로 들어옵니다. 정확한 추적이 필요하면 프롬프트에 "LSP로"를 명시합니다.

적합한 사용 시점
  • get_db 같은 의존성 함수, 서비스 함수가 어디서 쓰이는지 찾을 때 (영향 범위의 1차 근거)
  • 라우터 → 함수 → DB 호출까지 호출 계층을 거슬러 올라갈 때
  • 함수를 다른 모듈로 옮긴 직후 import 누락·시그니처 불일치를 잡을 때
부적합하거나 주의할 상황
  • Depends()로 주입되는 의존성, 문자열로 지정한 라우트, getattr 같은 동적 호출은 정적 분석으로 완전히 추적되지 않을 수 있습니다(추정). 이런 부분은 code-explorer의 실행 흐름 추적으로 보완합니다.
  • 가상환경을 활성화하지 않고 Claude를 시작하면 서드파티 import를 미해결로 오보할 수 있습니다. venv 활성화 후 claude를 실행하고, 필요하면 pyrightconfig.json에 venvPath를 지정합니다.
  • 프로젝트 인덱싱 중 메모리 사용량이 커질 수 있습니다. 클라우드 세션에서는 동작하지 않습니다.

feature-dev 코드 추적·설계

핵심 역할

특정 기능의 실행 경로를 끝까지 따라가고(code-explorer), 그 결과를 바탕으로 레이어 분리 설계안을 여러 개 비교하며(code-architect), 바뀐 코드를 CLAUDE.md 기준으로 검토(code-reviewer)합니다. 이 프로젝트에서는 주로 에이전트를 단독 호출해 "추적"과 "설계 결정"에 씁니다.

내부 동작 방식
  • code-explorer: 진입점, 호출 체인, 데이터 흐름·변환, 아키텍처 레이어, 의존성을 분석해 file:line이 붙은 단계별 실행 흐름과 꼭 읽어야 할 파일 목록을 돌려줍니다.
  • code-architect: 기존 패턴과 관례를 분석한 뒤 설계를 결정하고 컴포넌트 설계, 수정 파일 지도, 구현 순서를 만듭니다. /feature-dev 안에서는 "최소 변경 / 클린 아키텍처 / 실용적 균형" 세 관점으로 병렬 실행됩니다.
  • code-reviewer: CLAUDE.md 준수, 버그, 품질을 검토하고 신뢰도 80 이상인 이슈만 보고합니다.
  • /feature-dev 전체 흐름은 7단계(요구 확인 → 탐색 → 질문 → 설계 → 구현 → 리뷰 → 요약)이며, 질문·설계 선택·구현 승인·리뷰 대응에서 멈추고 사용자 결정을 기다립니다.
Claude Code와의 상호작용 방식

superpowers TDD·테스트 보강

핵심 역할

Claude에게 "테스트 먼저, 실패 확인, 최소 구현, 정리"라는 RED-GREEN-REFACTOR 규율을 강제하는 스킬 묶음입니다. 레거시 리팩토링에서는 "현재 동작을 고정하는 보호 테스트를 먼저 쓰고, 그 테스트가 깨지지 않게 구조를 바꾸는" 규율로 씁니다.

내부 동작 방식
  • 명령이나 훅보다 스킬 중심입니다. 작업 단계에 맞는 스킬을 Claude가 자동으로 불러오며, /superpowers:<스킬명>으로 직접 부를 수도 있습니다.
  • 이 프로젝트와 관련 깊은 스킬:
    • test-driven-development — 구현 중 활성화. 테스트를 먼저 쓰고 실패를 확인한 뒤에만 구현 코드를 추가하게 하며, 테스트 안티패턴 참고 자료를 포함
    • verification-before-completion — "완료"라고 말하기 전에 실제로 테스트를 돌려 증명하게 함
    • systematic-debugging — 테스트가 깨졌을 때 추측 대신 원인을 좁혀 가게 함
    • writing-plans, subagent-driven-development — 계획을 작은 작업으로 쪼개고 작업마다 새 서브에이전트에 맡긴 뒤 명세 준수·코드 품질 2단계 리뷰
    • using-git-worktrees — 깨끗한 테스트 기준선을 확인한 격리된 작업 공간 생성
    • dispatching-parallel-agents — 서로 독립적인 작업 2개 이상을 병렬 에이전트로 나눔 (4단계 도메인별 계약 테스트)
    • receiving-code-review — 리뷰 지적을 그대로 따르지 않고 기술적으로 검증한 뒤 반영 (10단계)
    • finishing-a-development-branch — 테스트 통과 확인 후 통합 방식 선택. 이 가이드는 1번 "로컬 병합"만 사용 (11단계)
Claude Code와의 상호작용 방식

켜 두면 구현 단계마다 Claude가 스스로 스킬을 적용합니다. 사용자는 "TDD로", "먼저 실패하는 테스트부터"라고 말하거나 스킬을 직접 지정합니다. 실패 → 통과 → 정리의 각 결과가 대화에 보이므로 RED 단계에서 테스트가 의도를 맞게 표현하는지 검토할 수 있습니다.

code-simplifier 코드 단순화

핵심 역할

동작은 그대로 두고 "어떻게 쓰였는지"만 개선하는 단일 에이전트입니다. 구조 리팩토링이 끝난 뒤 가독성 마무리에 씁니다.

내부 동작 방식
  1. 기능 보존: 출력과 동작을 바꾸지 않음
  2. 프로젝트 규칙 적용: CLAUDE.md의 코딩 규칙을 따름
  3. 명확성 향상: 불필요한 중첩·중복 제거, 이름 개선, 뻔한 주석 제거, 중첩 삼항 대신 if/else
  4. 균형: 줄 수를 줄이려고 가독성을 해치거나 유용한 추상화를 없애지 않음
  5. 범위 한정: 따로 지시하지 않으면 현재 세션에서 최근 수정된 코드만

요청이 없어도 코드 작성·수정 직후 스스로 다듬도록 설계돼 있습니다.

Claude Code와의 상호작용 방식

"code-simplifier로 다듬어줘"처럼 호출하거나 자동 실행됩니다. 바꾼 내용 중 이해에 영향을 주는 것만 요약해 보고합니다.

적합한 사용 시점

부적합하거나 주의할 상황
  • 에이전트 정의의 기본 규칙 예시는 ES 모듈, function 키워드, React 패턴 등 JavaScript/TypeScript 중심입니다. CLAUDE.md에 Python 규칙(타입 힌트 필수, async def 사용 기준, 예외 처리 방식, Ruff 규칙 등)을 적어 두어야 의도대로 동작할 것으로 봅니다(추정).
  • 구조 변경(레이어 이동)용이 아닙니다. 구조가 정리되기 전에 쓰면 곧 옮길 코드를 다듬는 셈이 됩니다.
  • "자동 실행" 특성 때문에 보호 테스트 없이 돌리면 미묘한 동작 변화를 놓칠 수 있습니다. 항상 테스트를 다시 돌립니다.

claude-code-setup + hookify 프로젝트 맞춤 자동화

두 플러그인은 짝으로 씁니다. claude-code-setup이 "무엇을 자동화할지" 추천하고, hookify가 그중 규칙을 실제 훅으로 만듭니다.

핵심 역할
  • claude-code-setup: 코드베이스를 훑고 이 저장소에 맞는 자동화를 범주별로 1~2개씩 추천합니다 — MCP 서버, 스킬, 훅(자동 포맷·린트, 민감 파일 차단), 서브에이전트(보안·성능 리뷰어), 슬래시 명령. 읽기 전용이라 파일을 수정하지 않습니다.
  • hookify: hooks.json을 직접 편집하지 않고, 자연어 설명이나 최근 대화 분석으로 마크다운 규칙 파일을 만들어 경고·차단 훅을 겁니다.
내부 동작 방식 (hookify)
  • /hookify <설명> → .claude/hookify.<이름>.local.md 생성. 인자 없이 실행하면 최근 대화에서 사용자가 교정했던 행동을 찾아 규칙을 제안합니다.
  • 규칙 파일 = YAML 프런트매터 + 표시할 메시지. 필드: event(bash / file / stop / prompt / all), pattern 또는 conditions, action(warn 기본 / block)
  • block은 PreToolUse에서 실행을 막고, stop 이벤트에서는 종료를 막습니다. 재시작 없이 다음 도구 사용부터 적용됩니다.
  • 관리: /hookify:list, /hookify:configure, /hookify:help
Claude Code와의 상호작용 방식

claude-code-setup은 "이 프로젝트에 맞는 자동화를 추천해줘"처럼 자연어로 호출하면 스킬이 실행되어 추천 목록을 돌려줍니다. hookify 규칙은 조건이 맞으면 Claude의 도구 호출 직전·직후·종료 시점에 메시지를 끼워 넣거나 막습니다.

적합한 사용 시점
  • 0단계 준비: claude-code-setup으로 추천을 받고, 필요한 규칙을 hookify로 생성
  • 리팩토링 중 같은 실수를 두 번 이상 교정했을 때 /hookify로 규칙화

세 번째 규칙은 오탐 범위가 좁아 처음부터 block입니다(0단계에서 생성).

부적합하거나 주의할 상황
  • hookify는 정규식 매칭이라 의미 기반 판단(예: "이 함수가 비즈니스 로직인가")은 못 합니다. 그런 판단은 code-reviewer와 CLAUDE.md에 맡깁니다.
  • 규칙이 많거나 event: all·복잡한 정규식이면 매 도구 호출이 느려집니다. Python 3.7+ 필요.
  • block 규칙을 너무 넓게 걸면 정상 작업까지 막습니다. 처음에는 warn으로 시작합니다.
  • ralph-loop도 Stop 훅을 쓰므로 require-pytest-before-stop(stop block)과 겹칩니다. 루프를 돌리는 동안에는 이 규칙을 warn으로 낮춥니다(추정, ralph-loop 참조).
  • claude-code-setup의 추천에는 외부 MCP가 포함될 수 있으니, 로컬 전용 원칙에 맞는 것만 고릅니다.

commit-commands 로컬 Git 커밋

핵심 역할

변경 내용을 분석해 저장소의 기존 커밋 스타일에 맞는 메시지로 커밋합니다. 이 프로젝트에서는 /commit만 씁니다. /commit-push-pr은 원격 push와 gh pr create가 필요하고, /clean_gone은 원격에서 삭제된 브랜치 정리용이라 로컬 전용 환경에서는 쓰지 않습니다.

내부 동작 방식 (/commit)
  1. git status 분석
  2. staged·unstaged 변경 검토
  3. 최근 커밋 메시지로 저장소 스타일 파악
  4. 커밋 메시지 초안 작성 (conventional commit 관례)
  5. 관련 파일 staging — .env, credentials.json 같은 비밀 파일은 제외

skill-creator 확장 · 채택 · 반복 절차 고정

핵심 역할

Anthropic이 만든 스킬 작성·개선·평가 도구입니다. 5~8단계는 엔드포인트마다 같은 절차(설계 → 서비스 단위 테스트 → 이동 → 계약 테스트 → 커밋)를 반복합니다. 첫 엔드포인트를 끝낸 뒤 그 절차를 프로젝트 스킬로 고정하면, 두 번째부터는 같은 품질로 반복되고 프롬프트를 매번 길게 쓸 필요가 없습니다.

핵심 역할

ponytail 확장 · 범위 한정 · 과설계 점검

핵심 역할

개인 개발자(DietrichGebert)가 별도 마켓플레이스로 배포하는 플러그인(MIT, v5.2.0)입니다. "요청되지 않은 추상화·옵션·의존성을 만들지 말고, 가장 짧은 완전한 변경을 하라"는 규칙을 세션 시작 훅으로 상시 주입하고, 보고 전용 점검 명령을 제공합니다. 이 가이드에서는 AI가 쓴 변경분의 과설계를 찾아내는 보고 도구로만 씁니다. 코드를 다듬는 일은 code-simplifier가 맡습니다.

내부 동작 방식
  • 훅 3개: SessionStart(규칙 주입), SubagentStart(하위 에이전트에도 주입), UserPromptSubmit(레벨 추적). 훅 스크립트에는 네트워크 호출이 없습니다(코드 확인).
  • /ponytail-review: 커밋되지 않은 변경(없으면 마지막 커밋)을 대상으로 버그 → 위험 → 확장성 → 테스트 없는 위험 로직 → 느린 코드 → 군더더기 순서로 보고합니다.
  • /ponytail-audit: 같은 관점으로 저장소 전체(또는 지정 폴더)를 점검합니다. 죽은 코드, 중복 헬퍼, 구현이 하나뿐인 추상화도 찾습니다.
  • /ponytail-debt: 코드의 shortcut: 주석을 모아 "한계 · 다시 볼 조건" 대장을 만들고, 조건이 없는 항목을 no-trigger로 표시합니다. 보고만 하고 파일은 고치지 않습니다.
  • /ponytail lite|full|ultra|off: 상시 규칙의 강도를 바꿉니다.
Claude Code와의 상호작용 방식

설치하면 모든 세션에 규칙이 자동으로 들어갑니다. 점검 명령 3개는 사용자가 직접 시작하며, 결과는 보고서로만 받습니다.

적합한 사용 시점
  • 3단계: /ponytail-audit app/의 "군더더기" 항목을 위험도 표의 정리 후보 열에 참고 자료로 붙입니다.
  • 10단계: code-simplifier 다음에 /ponytail-review로, 이번 변경에 요청되지 않은 추상화·래퍼·의존성이 생겼는지 확인합니다.
  • 11단계 직전: /ponytail-debt로 미뤄 둔 임시방편을 대장으로 만들어 다음 작업 목록에 넘깁니다.
부적합하거나 주의할 상황
  • 5·6단계는 service·repository 계층을 새로 만드는 작업이라, "추상화를 만들지 마라"는 상시 규칙과 부딪힐 수 있습니다. 프롬프트에 "계층 분리는 요청 범위"라고 밝히거나, 이 구간에서는 /ponytail lite로 낮춥니다(추정).
  • 유지 주체가 개인이고, 마켓플레이스가 GitHub 저장소를 직접 가리켜 sha로 고정되지 않습니다. 업데이트 때 규칙이 바뀔 수 있으니 버전을 확인합니다(신뢰성 기준 1·4 미충족 → 범위 한정).
  • /ponytail-gain은 공개 벤치마크 수치만 보여 주는 명령이라, 이 프로젝트의 효과 측정 근거로 쓰지 않습니다.

다른 플러그인과의 협업

지적 사항은 superpowers receiving-code-review로 검증한 뒤 반영하고, 실제 단순화 편집은 code-simplifier에 맡깁니다. code-modernization의 architecture-critic이 설계 단계(5단계)에서 과잉 설계를 견제한다면, ponytail은 구현이 끝난 변경분(10단계)에서 같은 일을 합니다.

plugin-dev 조건부 · 8단계

무엇

Anthropic의 플러그인 개발 도구 모음입니다. 스킬 7개(훅·명령·에이전트·스킬·MCP·설정·구조)와 에이전트 3개(agent-creator, plugin-validator, skill-reviewer)로 이루어져 있습니다. 이 프로젝트에서 의미가 있는 것은 hook-development 스킬의 프롬프트 기반 훅("type": "prompt")입니다.

조건

hookify는 정규식이라 "async def 함수 안에서 호출된 동기 함수가 결국 블로킹 I/O를 하는가" 같은 판단을 못 합니다. 이런 간접 호출이 반복해서 문제가 될 때만 씁니다.

시나리오 — 8단계
plugin-dev의 hook-development 스킬로, app/ 아래 .py 파일을 편집할 때 "새로 추가된 코드가 async def 안에서 requests·time.sleep·동기 세션·open()을 직접 또는 간접 호출하는가"를 판단하는 PostToolUse 프롬프트 훅을 프로젝트 .claude/settings.json에 만들어줘. 처음엔 경고만.
주의

프롬프트 훅은 조건이 맞을 때마다 모델을 호출하므로 편집마다 지연과 비용이 생깁니다. 대상 경로를 좁히고, 같은 규칙을 hookify 정규식으로 잡을 수 있으면 그쪽을 씁니다.

playwright 조건부 · 10단계

무엇

Microsoft의 브라우저 자동화 MCP를 로컬에서 실행합니다(npx @playwright/mcp@latest). 페이지 이동·입력·클릭·스크린샷이 가능합니다.

조건

FastAPI가 Jinja 템플릿 화면이나 관리자 화면을 제공할 때만 씁니다. JSON API만 있는 프로젝트는 계약·통합 테스트(httpx)로 충분합니다.

시나리오 — 10단계, 화면이 있는 경우
playwright로 로컬 서버(127.0.0.1:8000)에서 로그인 → 주문 생성 화면 → 제출 → 주문 상세 표시를 확인하고 단계별 스크린샷을 남겨줘. 확인된 흐름은 pytest-playwright 테스트로 옮겨줘.
주의

플러그인 설정이 @latest라 실행할 때마다 다른 버전이 받아질 수 있고, 패키지 버전이 아직 0.0.x대입니다. 안정성을 원하면 같은 MCP를 프로젝트 .mcp.json에 버전을 고정해(@playwright/mcp@0.0.83 등) 직접 등록합니다.

serena 조건부 · 5·6단계

무엇

언어 서버 기반의 심볼 탐색·편집 MCP입니다. pyright-lsp의 LSP 도구가 조회 전용인 것과 달리, 심볼 단위 편집(본문 교체, 심볼 앞뒤 삽입, 이름 변경)을 제공합니다.

조건

5·6단계에서 함수·클래스를 여러 모듈로 대량 이동하거나 이름을 바꿀 때 텍스트 치환보다 안전한 편집이 필요할 때.

기본은 보류하는 이유
  • 플러그인 설정이 uvx --from git+https://github.com/oraios/serena라 기본 브랜치의 최신 코드가 실행됩니다. 버전이 고정되지 않습니다.
  • 애플리케이션이 GPL-3.0-or-later입니다. 개발 도구로 로컬에서 쓰는 데는 보통 문제가 없지만, 조직 정책을 확인해야 할 수 있습니다.
  • pyright-lsp와 언어 서버 기능이 겹칩니다. 한 엔드포인트씩 작게 옮기는 이 가이드의 방식에서는 Claude의 기본 편집 + pyright 진단으로 충분한 경우가 많습니다.

쓰기로 하면 PyPI 패키지 버전을 고정해 .mcp.json에 직접 등록합니다.

context7 조건부 · 6·7·8단계

무엇

Upstash가 호스팅하는 원격 MCP(https://mcp.context7.com/mcp)로, 라이브러리의 최신 문서와 예제를 조회합니다.

조건

로컬 전용 원칙을 "코드가 밖으로 나가지 않는다" 수준으로 해석하고 문서 조회는 허용할 때만 씁니다. 6단계(SQLAlchemy 2.0 비동기 로딩 전략), 7단계(Pydantic v2 직렬화 옵션), 8단계(Starlette run_in_threadpool, anyio)에서 학습 데이터보다 새로운 API를 확인할 때 유용합니다.

주의

질의 문자열은 외부 서버로 갑니다. 프롬프트에 코드 조각이 섞이면 그것도 함께 나갈 수 있습니다(추정). 엄격한 로컬 전용이면 제외합니다.

lumen 조건부 · 1·2단계

무엇

Ory가 만든 로컬 의미 검색 MCP입니다. 코드를 파싱해 로컬 임베딩 서버(Ollama 또는 LM Studio)로 색인하고 SQLite에 저장합니다. README는 API 키 없이 "100% local"이라고 설명합니다.

조건

코드베이스가 커서 "할인 계산하는 곳 전부", "재고를 깎는 곳 전부"처럼 이름이 제각각인 코드를 찾아야 할 때. 소규모 프로젝트는 grep + pyright-lsp + code-explorer로 충분합니다.

주의

Ollama를 설치하고 임베딩 모델을 받아야 하며, 첫 색인에 시간이 걸립니다. 의미 검색 결과는 후보 목록이므로, 영향 범위의 최종 근거는 pyright-lsp 참조 찾기로 확정합니다.

sonarqube 조건부 · 3·9·10단계

무엇

SonarSource의 공식 플러그인입니다. SonarQube CLI와 MCP 서버를 연결해 이슈 조회, 커버리지·중복 지표, 품질 게이트 확인, 비밀값 스캔 훅을 제공합니다.

조건

조직이 이미 SonarQube를 쓰거나, Community Build를 로컬 Docker로 띄워 결정적 규칙 기반 품질 게이트를 두고 싶을 때. 3단계(위험도 근거: 복잡도·중복·커버리지), 9단계(보안 핫스팟), 10단계(품질 게이트)에 씁니다.

주의

SonarQube 계정(Cloud, Server 또는 Community Build), sonar CLI, 컨테이너 런타임, Node.js가 필요해 준비 비용이 큽니다. SonarQube Cloud를 쓰면 코드 분석 결과가 외부로 나가므로 로컬 전용 원칙과 충돌합니다. 라이선스는 Source-Available입니다.

실패 시 대응

중간 커밋에서 테스트가 깨지면 묶음 순서를 바꾸거나 인접 묶음과 합침. 잘못 커밋했으면 아직 원격이 없으므로 git reset --soft HEAD~1로 되돌려 다시 나눔(되돌리기 전 사용자 확인). security-guidance 커밋 리뷰가 고심각도를 보고하면 커밋을 멈추고 9단계로 돌아감

작업 브랜치 마무리 — finishing-a-development-branch

작업 브랜치(0단계의 refactor/orders, 또는 using-git-worktrees로 만든 작업 공간)에서 커밋을 나눈 뒤 이 스킬로 테스트 통과를 다시 확인하고, 선택지 중 1번 "Merge back to base-branch locally"만 고릅니다. 0단계의 block-remote-git 규칙이 실수로 2번(push·PR)을 고르는 것을 막아 줍니다.

확인된 것과 추정

확증공식 문서·README·에이전트 정의에서 직접 확인 — 각 플러그인의 명령·에이전트·스킬·훅 구성, LSP 도구의 조회 기능, security-guidance의 3계층과 데이터 전송 범위, claude-security의 산출물과 패치 흐름, claude-code-setup이 읽기 전용이라는 점, hookify 규칙 형식, commit-commands 중 /commit-push-pr이 gh와 원격을 요구한다는 점, superpowers가 공식 마켓플레이스에 등재돼 있고 test-driven-development 스킬을 포함한다는 점. 확장 검토 — 마켓플레이스 등재 여부·작성자·소스 고정 방식(marketplace.json, 2026-10-13 커밋), 각 MCP의 실행 명령·URL(.mcp.json), code-review의 gh 전용 도구 허용 목록, ralph-loop의 --max-iterations 기본값 무제한과 jq 사용, plugin-dev의 프롬프트 기반 훅 지원, pydantic 스킬의 다루는 범위(v1→v2 이관 항목 없음), serena의 라이선스 구성, semgrep·sonarqube·postman·codspeed의 로그인 요구(README), lumen의 로컬 임베딩 구조(README), code-modernization의 review·status·harden·verify 명령과 version-delta-analyst 에이전트 정의, superpowers의 finishing-a-development-branch 선택지. ponytail의 훅 3종·명령 6종 정의와 훅 스크립트에 네트워크 호출이 없다는 점(v5.2.0 설치본), typescript-lsp가 담당하는 확장자 목록(marketplace.json).

가상 예시문서 안의 모든 대화·출력 예시(파일 경로, 점수, 규칙 카드, 보안 발견)는 동작을 설명하려고 만든 것이며 실제 실행 결과가 아닙니다.

추정

  • 리팩토링 전용 플러그인: 공식 마켓플레이스에서 이름이 "refactor"인 공식 플러그인은 찾지 못해 code-modernization을 동등 기능으로 선정했습니다. 같은 저장소 안의 제자리 리팩토링에는 transform보다 진단 명령과 에이전트를 떼어 쓰는 방식이 맞을 것으로 봅니다.
  • Depends() 주입, 동적 라우트는 pyright 정적 분석만으로 완전히 추적되지 않을 수 있습니다.
  • superpowers TDD로 특성화 테스트를 쓸 때는 "바로 통과해야 한다"고 명시해야 혼선이 없습니다.
  • pr-review-toolkit은 원격 PR 없이 로컬 git diff로 충분히 동작합니다(README 사용 예 근거).
  • code-simplifier가 Python에서 의도대로 동작하려면 CLAUDE.md에 Python 규칙이 필요합니다.
  • /commit이 여러 관심사를 자동으로 여러 커밋으로 나누지는 않으므로, 논리 단위 분리는 사용자가 범위를 지정해야 합니다.
  • 외부 저장소 플러그인은 마켓플레이스에 고정된 sha의 코드가 설치될 것 — 설치 동작은 실행해 보지 않았습니다.
  • ralph-loop와 hookify stop 규칙을 함께 쓸 때의 상호작용.
  • ponytail 상시 규칙이 5·6단계의 계층 신설 작업을 실제로 방해하는지, /ponytail lite로 충분한지.
  • context7 질의에 프롬프트의 코드 조각이 포함될 수 있다는 점.
  • serena가 소규모 이동에서는 기본 편집 대비 이득이 작다는 판단.
  • 2026-10-14 재검토에서 최종 후보 약 14개를 뺀 나머지 약 250개는 이름과 설명만으로 제외했으며, 저장소를 열어 보지는 않았습니다.

실행하지 않은 것확장 플러그인을 실제 FastAPI 프로젝트에서 설치·실행하지 않았습니다. 확장 시나리오의 프롬프트와 기대 결과도 동작 설명을 위한 예시입니다. 2026-10-14 재검토 후보도 설치·실행하지 않았습니다. GitHub 별 수·최근 이슈 같은 활동 지표는 조회할 수 없어 선정 기준에서 뺐습니다.

모름code-modernization transform의 목표 스택 인자를 FastAPI 레이어드 구조로 어떻게 표기해야 가장 잘 해석되는지.

데이터 전송 주의 — security-guidance와 claude-security는 리뷰를 위해 diff와 관련 파일 내용을 설정된 모델 엔드포인트(기본 Anthropic API)로 보냅니다. GitHub 연동은 아니지만 "코드가 로컬 밖으로 나가지 않아야 하는" 환경이라면 사전 확인이 필요합니다.

# stage-pilot

워크플로 단계마다 **어느 플러그인을 어떤 순서로 쓰고, 어디서 멈춰 승인받고, 무엇으로 완료를 확인하는가**를 `references/stage-map.json` 한 곳에서 읽어 안내·수행한다. 레거시 리팩토링 트랙은 통합 가이드(`#selection`, `#stage-map`)와 시나리오 가이드 2종을 옮긴 것이고, 신규·기능 추가·고도화 트랙은 같은 플러그인 선정 기준을 그 작업에 맞게 배치한 것이다. 가이드를 고치면 이 파일도 함께 고친다.

## 트랙(프로필)

| 트랙 | 프로필 | 언제 | 단계 |
|---|---|---|---|
| 신규 | `greenfield` (별칭 `new`) | 코드가 없는 빈 폴더에서 시작 | 0 준비 · 1 기획 · 2 설계 · 3 기술 선정 · 4 작업 계획 · 5 구현 · 6 검증 · 7 보안 · 8 마무리 |
| 레거시 기능 추가 | `feature` (`--work <이름>`) | 동작 중인 코드에 기능을 더함 | 0 영향 분석 · 1 명세·설계 · 2 보호 테스트 · 3 계획 · 4 구현 · 5 리뷰·보안 · 6 커밋 |
| 레거시 리팩토링 | `default` (별칭 `refactor`) | 동작은 그대로, 구조를 개선 | 진입 전 · 0~11 (통합 가이드) |
| 레거시 고도화 | `enhance` (`--work <이름>`) | 성능·안정성·운영성·버전을 끌어올림 | 0 진단 · 1 목표·기준선 · 2 설계 · 3 보호 테스트 · 4 계획 · 5 실행 · 6 측정 · 7 보안·리뷰 · 8 커밋 |
| 시나리오 | `fastapi-default`, `g6` | 해당 시나리오 가이드를 따를 때 | 가이드의 단계 |

## 시작 — 트랙 고르기

상태 파일이 없는 프로젝트에서 새 프로젝트·기능 추가·리팩토링·고도화 요청이 오면, 훅이 `[stage-pilot] 프로젝트 상태 … 추천 트랙 …`을 넣는다(직접 확인: `stage.js detect`).

1. 프로젝트 상태(빈 폴더 / 코드 있음)와 요청 의도를 함께 본다. 둘이 어긋나면(코드가 있는데 "새 프로젝트") 그 사실을 먼저 알린다.
2. `set <profile> <첫 단계> [--auto] [--work <짧은-영문-이름>]`으로 시작한다. 사용자가 자동 승인을 요청했을 때만 `--auto`를 붙인다. `feature`·`enhance`는 작업 이름을 붙여 문서가 `docs/work/<이름>/`에 모이게 한다.
3. 한 트랙을 마치면(`next`가 "마지막 단계까지 완료"를 알림) 다음 작업은 새 트랙으로 `set` 한다. 결정 기록과 이력은 상태 파일에 이어서 쌓인다.

## 상태와 스크립트

- 상태 파일: 대상 프로젝트의 `.claude/stage-pilot/state.json` (`profile`, `stage`, `work`, `auto`, `decisions`, `history`, `completed`). 손으로 고치지 않고 항상 스크립트로 바꾼다.
- `node "${CLAUDE_PLUGIN_ROOT}/scripts/stage.js" <하위 명령>`
  - `status` 현재 단계 카드 · `profiles` 트랙 목록 · `detect` 빈 폴더/레거시 판별
  - `plan [stage]` 도구로 호출할 항목(`invoke`), 안내만 할 항목(`other`), 완료 확인 목록(`checks`), 단계 보고서 경로(`report`)
  - `check [stage]` 완료 확인 실행 — 문서 내용, ID 추적(R-·F-·E-가 계획·테스트까지 이어지는지), 테스트, 작업 트리 정리
  - `next [--force]` check 를 통과해야 다음 단계로 간다. `--force`는 사람이 판단해 넘길 때만
  - `set …`, `auto on|off`, `log "<결정>"`, `consent "<사용자가 비용을 승인한 문장 원문>"`
  - `skip <ref> "<근거>"` 조건부 항목을 쓰지 않은 근거, `reuse <ref> "<앞 단계·산출물·최신 확인>"` 같은 트랙의 앞 단계에서 이미 실행한 결과를 쓴 일, `fallback <ref> "<이유 → 한 일>"` 호출할 수 없어 직접 한 일. `ref`는 `plan`에 나온 이름 그대로(예: `superpowers:dispatching-parallel-agents`), 항목마다 한 번씩

## 제안 모드 (기본, `auto` 꺼짐)

요청이 단계 작업이거나 세션에 `[stage-pilot]` 안내가 있으면:

1. 현재 단계 카드(`status`)를 근거로 **주 플러그인 → 보조 → 조건부(조건 충족 시만)** 순서로 제안한다. 조건부는 조건을 한 줄로 확인하고 맞을 때만 권한다.
2. 요청이 다른 단계의 일이면(훅이 알려 줌) 첫 줄에 "이 요청은 N단계(제목), 현재는 M단계"처럼 **두 단계 번호를 모두** 밝히고, 그 사이 건너뛰는 단계와 위험을 알린 뒤 사용자가 고르게 한다. 건너뛰는 것 자체를 막지는 않는다.
3. 미설치 플러그인은 설치 명령을 보여 준다. `/plugin install`·`/plugin marketplace add`·`/mcp`는 사용자만 실행할 수 있다.
4. 실행은 하지 않는다. 실행은 `run`, "N단계 진행해줘" 같은 명시적 요청, 또는 자동 승인 모드일 때만.

## 수행 모드 (`run [stage]`, 명시적 요청, 또는 자동 승인 모드의 단계 작업 요청)

1. `plan [stage]`으로 호출 항목·완료 확인·보고서 경로를 받는다.
2. `invoke`의 항목을 **실제 도구 호출로** 처리한다. 같은 일을 직접 해 버리고 플러그인 호출을 생략하지 않는다 — 이 플러그인의 목적은 가이드가 정한 플러그인이 실제로 쓰이게 하는 것이다.

| type | 방법 |
|---|---|
| `skill` | Skill 도구로 `ref` 호출 (예: `superpowers:writing-plans`) |
| `agent` | Agent 도구, `subagent_type` = `ref` (예: `feature-dev:code-architect`). 프롬프트에 대상 경로·이번 단계 목표·`note`·앞 단계 문서 경로를 넣는다. 서로 독립인 에이전트는 한 메시지에서 병렬로 |
| `command` | Skill 도구로 `ref` 호출 (플러그인 명령은 `플러그인:명령` 이름으로 노출됨), `args`를 인자로 |
| `mcp` | 그 플러그인의 MCP 도구를 호출 (예: `context7` → 라이브러리 ID 확인 후 문서 조회) |
| `shell` | Bash로 실행. 파일을 바꾸는 명령은 제안 모드에서는 먼저 보여 주고 확인 |
| `user` | 실행하지 않고, 사용자가 입력할 명령을 그대로 보여 준다 (`/ralph-loop`, `/plugin`, `/mcp`, `claude mcp add` 등) |

   **이미 실행한 항목은 재사용한다.** 리팩토링 트랙처럼 앞 단계(예: 진입 전)와 뒤 단계(1·2단계)에 같은 분석 도구(`modernize-assess`·`modernize-map`·`modernize-extract-rules`·`modernize-review`·`code-explorer` 등)가 함께 놓인 경우, 같은 트랙에서 이미 실행했고 그 뒤 코드가 바뀌지 않았으면(또는 `modernize-status`로 최신임을 확인했으면) 다시 돌리지 않고 `reuse <ref> "<앞 단계 id> 산출물 <경로>, <최신 확인 방법>"`을 남긴다. 재사용은 수행으로 친다 — `fallback`으로 기록하지 않는다. 코드가 바뀌었으면 다시 실행한다.
   **사람에게 묻는 도구도 끝까지 수행한다.** `modernize-review`(규칙 카드 판정), `hookify`(규칙 확인), `skill-creator`(평가 검토), `brainstorming`(질문) 처럼 절차 중에 사람의 답을 받는 도구는, 자동 승인 모드에서는 질문 대신 「자동 결정 원칙」으로 답해 그 도구의 절차와 산출물 형식을 끝까지 채운다(예: 규칙 카드마다 `Not sure — 자동: 현재 동작을 계약으로 고정, 버그 후보`를 판정 파일에 기록). 이것은 대체 수행이 아니라 수행이다. 대화형 질문 도구(AskUserQuestion)가 없다는 이유로 `fallback`하지 않는다.
   **`fallback`은 그 도구로 목적을 이룰 수 없을 때만 쓴다.** 도구의 절차는 따랐는데 완료 기준의 일부를 확인할 수단이 없으면(예: ruff 미설치) `fallback`이 아니라 단계 보고서의 완료 기준에 "미확인 — <이유>"로 적는다. 여러 번 쓰는 명령(예: `commit-commands:commit`은 커밋 하나를 만든다)은 논리 단위마다 다시 호출한다 — 한 번만 부르고 나머지를 손으로 하지 않는다.
   **불러온 스킬의 절차를 끝까지 따른다.** Skill 도구로 불러 놓고 그 절차를 따르지 않으면 호출한 것이 아니다. 따를 수 없는 사정(필요한 도구·실행 파일이 없음 등)이 있으면 `fallback <ref> "<이유> → <한 일>"`로 기록하고, 사람이 고칠 수 있게 보고서에도 적는다. 같은 목적의 다른 항목이 `when` 으로 준비되어 있으면(예: `executing-plans` / `subagent-driven-development`) 조건에 맞는 쪽을 쓴다.
   **비용 확인을 요구하는 스킬(예: `claude-security`의 스캔 시작 확인):** 이런 스킬은 사용자 본인의 말로 된 비용 승인만 인정한다. 자동 승인 모드라는 사실만으로는 승인이 아니다.
   - 사용자가 요청에서 시간·토큰 비용을 직접 승인했으면(훅이 알려 줌) 그 문장을 **고치지 않고 원문 그대로** `consent "<원문>"`으로 기록한다.
   - 스킬을 부를 때 `consent` 기록이 있으면 `args` 끝에 `사용자 비용 승인(<날짜>): "<원문>"`을 붙인다. 원문을 지어내거나 바꾸지 않는다.
   - 기록이 없으면 그 스킬의 비용이 드는 작업은 하지 않고 `fallback <ref> "사용자 비용 승인 문장 없음 → <대신 한 검토>"`를 남긴 뒤 같은 목적의 다른 항목(예: `code-modernization:security-auditor`)으로 검토한다. 제안·수행 모드에서는 스킬의 확인을 사용자에게 그대로 보인다.
3. **문서 위치는 이 플러그인이 정한다.** 스킬이 기본 저장 위치를 따로 갖고 있어도(예: brainstorming·writing-plans 의 `docs/superpowers/…`) `note`나 완료 확인에 적힌 경로(`docs/project/…`, `docs/work/<이름>/…`)에 저장한다. 완료 확인이 그 경로를 읽기 때문이다.
4. `when`(조건)이 붙은 항목은 프로젝트를 보고 조건을 판정한다. 충족하면 호출하고, 충족하지 않으면 호출하지 않고 `skip <ref> "<근거(예: 독립 작업 묶음 1개)>"`를 남긴다. 여러 항목을 한 줄로 묶거나 이름을 줄이지 않는다 — 사람과 평가 도구가 항목별로 확인하기 때문이다. 판정 근거 없이 건너뛰지 않는다.
5. 호출할 수 없는 항목(플러그인이 없음, 프로젝트 스킬 `fastapi-layer-slice`·`layered-slice`가 아직 없음)은 건너뛰지 말고 **같은 목적을 직접 수행한 뒤** `fallback <ref> "<이유> → <한 일>"`로 남긴다.
6. 에이전트·리뷰 결과가 고칠 거리를 내면 그 단계의 목표 범위 안에서 실제로 고친다(보고만 하고 끝내지 않는다). 리뷰 지적은 `superpowers:receiving-code-review` 기준으로 검증한 뒤 반영한다.
7. **`.claude/` 쓰기가 거부되면**(비대화형 실행 등에서 Claude Code 가 민감 경로로 막음) 같은 내용을 `docs/stage-pilot/pending/<원래 경로에서 .claude/ 를 뺀 경로>`에 초안으로 두고(예: `.claude/hookify.block-remote-git.local.md` → `docs/stage-pilot/pending/hookify.block-remote-git.local.md`, `.claude/skills/x/SKILL.md` → `docs/stage-pilot/pending/skills/x/SKILL.md`) `log "승인 대기: <원래 경로> — 사용자 확인 후 옮김"`을 남긴다. 초안 경로에 `.claude`를 넣지 않는다(그 경로도 막힌다). 다른 방법으로 우회해 쓰지 않는다. 이렇게 초안으로 남긴 것은 그 도구를 **수행한 것**이다 — `fallback`으로 기록하지 않는다.
8. **단계 보고서**를 `plan`의 `report` 경로에 쓴다. 다음 형식을 따른다 — 다음 단계와 사람이 이것만 읽고 이어갈 수 있게:

```
# <profile> <N>단계 — <제목>
## 호출한 플러그인
| 항목 | 결과 |   (invoke 항목마다 한 줄: 호출함 → 결과 / 조건 불충족 → 근거 / 대체 수행 → 한 일)
## 산출물
(파일 경로와 한 줄 설명)
## 결정
(승인 지점의 결정과 근거 — 자동 모드면 log 와 같은 내용)
## 완료 기준
(done 항목마다 충족/미충족과 증거: 테스트 출력 마지막 줄, 문서 경로)
```

9. `check`를 실행해 모두 통과하면 단계를 마친다. 실패 항목은 그 단계 범위에서 채운 뒤 다시 확인한다.

## 신규 트랙의 문서 규칙

신규 프로젝트는 문서가 곧 관리 체계다. 아래 ID 를 일관되게 쓰고, 다음 단계 문서가 앞 단계 ID 를 인용하게 한다(`check`가 추적한다).

| 문서 | 반드시 담을 것 |
|---|---|
| `docs/project/01-requirements.md` | 목적·사용자, 기능 요구사항 `R-1…`(각각 수용 기준), 비기능 요구 `NFR-1…`(수치로), 범위 밖, 가정·미결 사항 |
| `docs/project/02-design.md` | 레이어 구조(router → service → repository → model, schema 분리), ERD(mermaid `erDiagram`), API 목록(메서드·경로·요청/응답·관련 `R-`), 트랜잭션 경계·오류 응답 정책, 채택하지 않은 안과 이유 |

구현(5단계)에서는 테스트 이름이나 docstring 에 관련 `R-` ID 를 적는다. 작업을 마칠 때마다 작업표의 상태를 갱신한다. 레거시 트랙도 같은 방식으로 `F-`(기능 추가)·`E-`(고도화) ID 를 쓴다.

## 승인 지점

- **제안·수행 모드(`auto` 꺼짐):** 승인 지점(`approval`)에 닿으면 멈춘다. 결과를 요약하고 결정할 항목을 질문으로 제시한 뒤 턴을 끝낸다.
- **자동 승인 모드(`auto` 켜짐):** 멈추지 않는다. 아래 원칙으로 결정하고, 결정마다 `log "<결정과 근거>"`로 남긴 뒤 계속한다. 질문(AskUserQuestion 등)을 하지 않는다. 호출한 스킬이 사용자에게 질문하라고 해도(brainstorming 등) 의뢰서·코드·앞 단계 문서에서 답을 찾고, 없으면 가장 보수적인 가정을 문서의 "가정" 절에 적고 진행한다.

### 자동 결정 원칙

| 결정 | 자동 선택 |
|---|---|
| 요구사항 범위 | 의뢰서에 있는 것만. 없는 기능은 넣지 않고 "범위 밖"에 적음. 모호하면 단순한 해석을 가정으로 기록 |
| 설계안 | 요구사항을 모두 덮는 안 중 계층·추상화가 가장 적은 안(architecture-critic 이 과잉으로 지적하지 않은 안) |
| 기술 선정 | 요구사항·NFR 이 요구하는 것만 추가. 같은 일을 하는 표준·안정 버전 우선(FastAPI + Pydantic v2 + SQLAlchemy 2.x + pytest·httpx). 버전은 설치해 확인한 값으로 고정 |
| 작업 순서 | 선행 관계 → 위험 높은 것 먼저 → 의존 적은 것 먼저 |
| 규칙 카드·문서와 실제 동작이 다름 | 현재 동작을 계약으로 고정하고 "버그 후보"로 기록 (리팩토링·고도화 중 동작 변경 금지) |
| 리팩토링 우선 도메인·순서 | 위험도 표에서 커버리지 낮고 변경 잦은 것 먼저. 동률이면 의존이 적은 것 |
| 기존 API 계약 변경(응답 필드·입력 허용 범위) | 기능 추가는 "추가만" 허용, 기존 필드 변경·삭제는 하지 않음. 리팩토링·고도화는 변경하지 않음 |
| 고도화 목표 | 측정 가능한 지표가 있고 비용이 낮은 후보부터, 한 번에 1~3개 |
| 보안 발견 | 두 도구가 함께 찾았거나 근거 코드가 명확한 것만 수정, 나머지는 기록 |
| 남은 리뷰 이슈 | 이번 단계 범위 안이면 수정, 밖이면 기록 |
| 커밋 | 로컬 커밋만, 단계·논리 단위로 |

### 자동 승인 대상이 아닌 것 (자동 모드에서도 하지 않음)

- 원격 저장소 작업(push, PR), 저장소 밖 파일 수정, 데이터·파일 대량 삭제
- `user` 항목(`/plugin`, `/mcp`, `/ralph-loop` 등) — 실행하지 않고 log로 "사용자 실행 필요"를 남김
- `.claude/` 쓰기 거부를 우회하는 일 — 승인 대기 초안으로 남김
- 테스트가 실패한 채로 다음 단계로 넘어가기 — 고치지 못하면 그 지점에서 멈추고 보고

## 단계 완료와 이동

- 제안·수행 모드: 단계 보고서와 `check` 통과를 확인한 뒤 사용자에게 다음 단계로 갈지 묻는다. 동의하면 `next`.
- 자동 승인 모드: 단계 보고서를 쓰고 `check`가 통과하면 `log`로 남기고 `next`. **마지막 단계도 `next`를 해야 트랙 완료가 기록된다** — 커밋으로 작업 트리를 정리한 뒤라도 그대로 `next`한다(상태 파일 `.claude/stage-pilot/`은 작업 트리 정리 판정에서 빠지고, 커밋하지 않아도 된다). `run … --through <stage>`가 주어졌으면 그 단계까지 같은 방식으로 이어서 수행한다.
- `check`가 실패하면 넘어가지 않는다. 채울 수 없는 항목은 "미확인"으로 보고서에 남기고 멈춘다.

## 다른 규칙

- `ralph-loop`는 첫 결과물이 승인된 뒤에만, `--max-iterations`를 붙여 사용자에게 제안한다. 설계 결정·보안 패치에는 쓰지 않는다.
- `ponytail`의 점검 명령은 보고 전용이다. 지적은 검증 후 반영하고, 계층을 새로 만드는 구간(default 5·6, fastapi-default 4~7, g6 7~11, 신규 5)에서는 `/ponytail lite`를 권한다.
- g6 프로필의 `code-modernization` 명령은 저장소 밖 `~/work/g6-analysis`에서만 실행한다(`workspace_note`).
- `context7`은 질의가 외부로 나가므로, 사용자가 외부 문서 조회를 허용했을 때만 쓴다. 허용 여부는 의뢰서(BRIEF 등)·CLAUDE.md·대화에서 찾아 **그 위치(파일:행)를 근거로** 적는다 — 기억이나 짐작으로 판정하지 않는다.
  - 허용 문장이 없으면 `skip context7 "<찾아본 파일들>에 허용 없음"`.
  - 허용됐는데 MCP 도구가 세션에 없으면(인증 전 `needs-auth` 등) `skip`이 아니라 `fallback context7 "허용됨(<파일:행>), MCP 미연결 — 사용자가 /mcp 에서 인증 필요 → <대신 확인한 방법>"`.
- 신규 트랙 8단계에서 CLAUDE.md 를 정리할 때, 의뢰서의 프로젝트 조건(외부 문서 조회 허용 여부, 운영 DB, 인증 방식 등)을 "프로젝트 조건" 절로 남긴다. 뒤 트랙(기능 추가·리팩토링·고도화)이 조건부 판정의 근거로 쓴다.
- `typescript-lsp`는 이 트랙들에서 쓰지 않는다(정적 JS 를 고칠 때만).
- `claude-security` 스캔은 Workflow 도구와 `python3` 실행 파일이 있어야 돈다. 없으면 스캔을 흉내 내지 말고 `fallback claude-security:claude-security "<없는 것> → <대신 한 검토>"`를 기록한 뒤 `code-modernization:security-auditor` 등으로 검토하고, 보고서에 해결 방법(예: Windows 는 `python3` 별칭 설치)을 적는다.

## 응답 형식

제안:
```
■ <트랙> <N>단계 — <제목>

실행할 것: 1) … 2) …
멈출 곳: <승인 지점>
완료 확인: <check 항목>
(미설치: <설치 명령>)
```

수행 후:
```
■ <트랙> <N>단계 수행 결과
호출한 플러그인: <ref> → <결과 한 줄> …
변경: <파일·테스트>
자동 결정: <log 한 내용> (자동 승인 모드일 때)
완료 확인: <check 결과> → 다음: <M>단계
```

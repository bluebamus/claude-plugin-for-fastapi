# work-memory — 작업·하위 작업·결정의 지속 기록

기억은 대화가 아니라 **대상 프로젝트의 파일**에 둔다. 세션이 끝나거나 대화가 압축돼도 SessionStart 훅이 단계 카드에 "작업 메모리"(열린 작업)와 "최근 결정"을 다시 넣는다.

| 무엇 | 어디 | 명령 |
|---|---|---|
| 트랙·단계·이동 이력 | `.claude/stage-pilot/state.json` | `stage.js set / next` |
| 작업·하위 작업 | 같은 파일 `tasks` | `stage.js task add / start / done / block / list` |
| 결정과 근거 | 같은 파일 `decisions` | `stage.js log "<결정 — 근거>"`, `skip / reuse / fallback` |
| 계획·추적표(사람이 읽는 원본) | `docs/project/04-work-plan.md`, `docs/work/<이름>/0x-plan.md` | 문서 편집 |
| 단계 결과 | `docs/stage-pilot/<작업>/<트랙>-<단계>.md` | 단계 보고서 |

## 절차

1. **세션 시작·재개:** 단계 카드의 작업 메모리를 먼저 읽는다. 더 필요하면 `stage.js task list` 와 현재 단계의 앞 단계 보고서를 읽는다. 기억에 기대 추측하지 않는다.
2. **계획 직후:** 작업 계획 문서의 `T-` 작업마다 `task add "T-3 상품 등록 API"` 를 만든다. 큰 작업은 하위 작업으로 쪼갠다:
   `task add "T-3a 스키마·검증" --parent W-<상위 작업을 add 할 때 출력된 번호>`(W- 번호는 추가 순서로 매겨져 T- 번호와 다르다). 제목에 계획 문서의 `T-` 번호를 넣어 문서와 기록을 잇는다. 끝난 상위 작업 아래에는 추가할 수 없다 — 이어서 할 일이면 상위를 `task start` 로 다시 연다.
3. **작업 중:** 시작할 때 `task start W-n`, 끝나면 테스트 결과와 함께 `task done W-n "<테스트 명령> → 12 passed"`. 하위 작업을 다시 열면(`start`·`block`) 끝났던 상위 작업도 자동으로 다시 열린다. 상태가 바뀌면 옛 메모는 지워진다. 막히면 `task block W-n "<무엇을 기다리는지>"` 후 사용자에게 알린다. 하위 작업이 열려 있으면 상위 작업은 done 이 거부된다 — 남은 일을 숨기지 않기 위해서다.
4. **결정:** 설계안 선택, 범위 조정, 보류한 리뷰 지적, 계획 변경처럼 나중에 "왜 이렇게 했지?"가 나올 결정은 바로 `log` 한다. 형식: `"<결정> — <근거/대안>"`.
5. **계획 변경:** 계획 문서를 먼저 고치고, 그다음 task 를 추가·정리한다(문서가 원본).
6. **서브에이전트에 나눠 줄 때:** 맡기는 작업의 `W-` id 와 완료 기준을 프롬프트에 넣고, 결과를 받은 뒤 메인 세션에서 `task done` 한다(서브에이전트는 상태 파일을 바꾸지 않는다 — 동시 쓰기 방지).
7. **단계를 넘기기 전:** 이번 단계 작업이 모두 done 인지 `task list` 로 확인한다. 남기는 작업은 이유를 단계 보고서에 적는다.

## 의사결정에 쓰는 법

- 새 결정을 내리기 전에 "최근 결정"과 관련 단계의 `log` 를 확인해 앞선 결정과 충돌하지 않는지 본다. 뒤집을 때는 앞선 결정을 인용해 `log "<새 결정> — <앞 결정> 을 바꾼 이유"`.
- 여러 선택지가 있으면 설계 문서의 "채택하지 않은 안과 이유" 절과 `log` 에 함께 남긴다.

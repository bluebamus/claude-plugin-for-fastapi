# 레거시 온보딩 매뉴얼

목표는 "문서화"가 아니라 **신규 개발자가 이 문서만 읽고도 첫 수정 작업을 안전하게 시작할 수 있게 하는 것**이다. 그래서 무엇이 있는지 나열하기보다, 요청 하나가 실제로 어떤 파일을 지나 어디서 저장되는지, 어디가 위험한지, 무엇을 먼저 해 보면 되는지를 보여 준다.

## 원칙

- **소스는 읽기만 한다.** 분석 대상 저장소의 코드를 고치지 않는다. 산출물은 지정한 출력 경로에만 쓴다. 분석 도구가 만든 중간 산출물(`analysis/` 등)도 저장소에 커밋하지 않는다.
- **모든 주장에 근거를 붙인다.** 흐름·규칙·경계 설명에는 `path/to/file.py:42`·`application/controllers/Board.php:42` 형태의 근거를 붙인다. 근거 없는 문장은 신규 개발자가 검증할 수 없어 오히려 해가 된다.
- **확인과 추정을 나눈다.** 실행·테스트로 확인한 것은 `확인`, 코드만 읽고 판단한 것은 `추정`으로 표시한다. 문서 끝 「확인된 것과 추정」에 모은다.
- **도식은 증거의 요약이다.** 도식의 노드는 실제 모듈·클래스·테이블 이름을 쓰고, 도식 아래 캡션에 핵심 근거 위치를 적는다. 상상으로 그린 이상적 구조는 "목표 구조"라고 명시할 때만 쓴다.
- **비밀값은 싣지 않는다.** 설정 파일·`.env`에서 본 키·비밀번호·토큰은 `****`로 가린다.

## 절차

### 1. 범위 정하기

사용자에게서 다음을 확인한다. 대화에 이미 있으면 묻지 않는다.

- 대상 저장소 경로, 매뉴얼 이름(예: `myapp`)
- 출력 경로 — 기본값 `docs/onboarding/<이름>-onboarding-manual.html` (대상 저장소 안에 쓰기가 곤란하면 현재 작업 폴더)
- 독자 수준(신규 입사자 / 다른 팀 개발자)과 꼭 다룰 도메인·흐름이 있는지
- 실행해 봐도 되는지(로컬 DB·테스트 실행 가능 여부)

### 2. 근거 수집

쓸 수 있는 도구를 위에서부터 고른다. 없는 도구는 건너뛰고 다음 것으로 대신한다.

| 알고 싶은 것 | 1순위 | 대안 |
|---|---|---|
| 구성 목록·복잡도·기술 부채 | code-modernization `/modernize-assess` | 디렉터리 순회 + `wc -l` + 의존성 파일 |
| 호출 그래프·진입점·데이터 흐름 | code-modernization `/modernize-map`, codegraph `codegraph_context`·`codegraph_trace` | LSP 참조 찾기·호출 계층, grep |
| 요청 하나의 실제 실행 경로 | feature-dev `code-explorer` 에이전트(흐름별 병렬) | codegraph `codegraph_trace`, 직접 읽기 |
| 업무 규칙 | code-modernization `/modernize-extract-rules` | 서비스·검증 함수 직접 읽기 |
| 데이터 모델 | ORM 모델·마이그레이션 파일 | DDL, 설치 스크립트 |
| 실제 동작 확인 | 테스트 실행, 앱 기동 후 라우트 목록 출력 | (불가하면 전부 `추정`) |

- code-modernization은 `legacy/<이름>` 링크를 전제로 한다. 링크와 `analysis/` 산출물은 대상 저장소 밖(또는 gitignore된 위치)에 둔다.
- 탐색 에이전트는 흐름별로 나눠 병렬로 띄우고, 각자 file:line 목록과 DB 접근·외부 호출·커밋 위치·예외 처리 지점을 돌려받는다. 메인 대화에는 결론만 남긴다.

### 3. 대표 흐름 고르기

모든 엔드포인트를 설명하지 않는다. 신규 개발자가 가장 먼저 만날 **3~5개 흐름**을 고른다.

1. 가장 많이 쓰이는 조회 흐름
2. 대표 쓰기 흐름(검증 → 저장 → 커밋 → 응답)
3. 인증·권한이 걸리는 흐름
4. (있으면) 배치·스케줄러·비동기 작업
5. (있으면) 화면과 API처럼 같은 일을 두 경로로 하는 흐름 — 차이가 곧 함정이다

고른 이유를 매뉴얼 4장 첫머리에 한 줄씩 적는다.

### 4. 매뉴얼 작성

`assets/manual-template.html`을 복사해 채운다. 템플릿에 Mermaid 렌더링, 라이트·다크 테마, 목차, 확인/추정 표시가 들어 있으므로 스타일을 새로 만들지 않는다.

장 구성(템플릿의 `id`와 같다). 해당 없는 장은 지우지 말고 "이 프로젝트에는 해당 없음 — 이유"를 한 줄 적는다. 빈 장이 있으면 독자가 빠뜨린 것인지 없는 것인지 구분할 수 없기 때문이다.

| id | 장 | 필수 도식 (Mermaid) |
|---|---|---|
| `overview` | 1. 한눈에 보기 — 무엇을 하는 시스템인가, 스택, 규모 숫자 | `flowchart` 시스템 컨텍스트(사용자·외부 시스템·DB) |
| `setup` | 2. 로컬에서 실행하기 — 설치·설정·기동·테스트 명령과 흔한 실패 | (선택) `flowchart` 기동 순서 |
| `structure` | 3. 디렉터리·레이어 지도 — 폴더별 책임, 의존 방향 | `flowchart` 레이어·모듈 의존도 |
| `flows` | 4. 대표 요청 따라가기 — 흐름마다 단계표(file:line) | 흐름마다 `sequenceDiagram` 1개 |
| `data` | 5. 데이터 모델 — 핵심 테이블과 관계, 동적 테이블 등 특이점 | `erDiagram` |
| `states` | 6. 상태 전이 — 주문·게시글 등 상태가 있는 엔티티 | `stateDiagram-v2` |
| `rules` | 7. 업무 규칙 — Given/When/Then 카드, 근거, 신뢰도 | (없음, 카드) |
| `boundaries` | 8. 트랜잭션·세션·비동기 경계 — 누가 커밋하는가, 세션 수명, async 안의 동기 호출 | `flowchart` 또는 `sequenceDiagram` |
| `risks` | 9. 위험 지도와 함정 — 테스트 공백, 중복 구현, 숨은 부수효과 | (선택) `quadrantChart` 위험도×변경 빈도 |
| `learning` | 10. 학습 경로와 실습 — 읽는 순서, 따라 해 볼 과제와 기대 결과 | (선택) `journey` 또는 `timeline` |
| `glossary` | 11. 용어집 — 도메인 용어·약어와 코드상 이름 대응 | (없음, 표) |
| `evidence` | 12. 확인된 것과 추정 — 실행한 명령과 결과, 추정 목록, 실행하지 않은 것 | (없음) |

도식을 쓰기 전에 `references/diagram-guide.md`를 읽는다. 장별 도식 패턴과, 렌더링을 깨뜨리는 Mermaid 문법 함정이 정리돼 있다.

**10장 실습**은 이 매뉴얼의 핵심이다. "글쓰기 요청에 로그를 하나 추가하고 4장 시퀀스도의 어느 단계에서 찍히는지 확인하기"처럼, 4~8장을 읽었으면 할 수 있고 결과를 스스로 확인할 수 있는 과제를 3개 이상 만든다. 각 과제에는 관련 장 링크, 손댈 파일, 기대 결과, 확인 명령을 적는다.

### 5. 검증

```bash
python scripts/check_manual.py <출력 HTML 경로>
```

검사 항목: 12개 장 `id` 존재, Mermaid 블록 수와 종류, 블록마다 캡션, flowchart의 `subgraph`/`end` 짝, file:line 근거 수, 확인/추정 표시, 남은 템플릿 자리표시자(`TODO:`). 실패 항목을 고친 뒤 다시 돌린다.

`npx`를 쓸 수 있으면 `--render`를 붙여 Mermaid CLI로 실제 렌더링까지 확인한다(처음 실행 시 패키지를 내려받음). 쓸 수 없으면 최종 보고에 "도식 렌더링은 브라우저에서 확인 필요"라고 남긴다.

### 6. 보고

사용자에게 다음을 짧게 알린다: 출력 경로, 다룬 대표 흐름, 도식 수, 근거 수, `추정`으로 남은 핵심 항목, 실행하지 못한 것. 매뉴얼을 팀과 공유할 계획이면 공유 페이지로 게시할 수 있다고 한 줄 제안한다.

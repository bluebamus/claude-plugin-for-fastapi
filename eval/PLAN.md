# stage-pilot v0.3 실전 평가 작업 계획

작성 2026-10-19, 최종 갱신 2026-10-21. 이 문서는 평가를 어떻게 하는지 정한다. 결과는 `RESULTS.md`에 쓴다.

**상태: 완료.** 최종본(판 L)으로 실전 6회차를 모두 통과했다(1~5회차 5회 연속, 6회차는 환경 손상 복구 뒤 재판정). E1~E6을 마쳤고, main 반영만 사용자가 실행한다.

## 원칙

- **플러그인은 범용이다.** `stage-pilot`은 특정 프로젝트를 모른다. 트랙은 4개뿐이다: 신규(`greenfield`), 기능 추가(`feature`), 리팩토링(`default`), 고도화(`enhance`).
- **두 시나리오 문서는 검증에만 쓴다.** 대상 문서는 `docs/scenario-plugin-guide/g6-refactoring-guide.html`과 `fastapi-default-project-structure-refactoring-guide.html`이다.
  - 문서에서 뽑은 프로젝트·과제·조건은 `eval/real/`에만 둔다.
  - 플러그인 세션에는 사용자가 실제로 할 법한 자연어 요청만 준다. 문서의 단계 번호나 도구 목록은 주지 않는다.
  - 문서의 단계표는 채점할 때 "문서가 기대한 산출물·도구가 나왔는가"를 대조하는 데만 쓴다.
- **연속 통과는 같은 판으로 센다.** 플러그인을 고치면 판을 올리고 처음부터 다시 센다. 하네스만 고친 경우는 저장된 로그로 재판정한다.

## 작업 단계

### E1. 범용화 (플러그인)

- `stage-map.json`에서 `fastapi-default`·`g6` 프로필을 지운다.
- SKILL.md·README·명령 문서·테스트·매뉴얼에 남은 두 프로젝트 전용 문구를 지운다.
- `legacy-onboarding-manual`의 예시 이름도 일반 이름으로 바꾼다.
- 테스트 명령을 범용으로 정한다.
  - `uv.lock`이 있으면 `uv run pytest -q`를 쓴다.
  - `set … --test "<명령>"`으로 바꿀 수 있게 한다. 마커 제외나 환경 변수가 필요한 프로젝트용이다.
  - 단위 테스트로 확인한다.

### E2. 실전 환경 기준선

| 프로젝트 | 원본 | 고정 | 기준선 확인 |
|---|---|---|---|
| g6 | `https://github.com/gnuboard/g6.git` | 클론한 커밋 해시를 기록 | Python 3.11, `fastapi==0.110.3`으로 `import main` 성공. 테스트 0건(문서 P1) |
| fastapi-default | `https://github.com/bluebamus/fastapi-default-project-structure.git` | 클론한 커밋 해시를 기록 | Python 3.13+, `uv sync --locked`. 고정 커밋 `49d9ee5`에서 Redis 포함 1,075 passed + MySQL 마커 18 passed, 실패 0 — 문서의 "4 failed"는 재현되지 않아 과제에서 뺐다 |

- 원본은 한 번만 클론해 `eval/real/cache/`(git 제외)에 둔다. 회차마다 사본에서 시작한다. 원격은 쓰지 않는다.
- Redis·MySQL이 필요하면 WSL 도커에 평가 전용 컨테이너를 새 포트로 띄운다(`sp-eval-redis` 6379, `fastapi-structure-mysql-test` 3311). 이미 돌고 있는 3307~3309 서버는 건드리지 않는다.
- 평가 컨테이너 관리:
  - 하네스는 회차 시작 때와 산출물 감사 전마다 평가 컨테이너를 확인하고 켠다. Docker가 다시 시작되거나 세션이 프로젝트 절차대로 `compose down`을 해도 같은 조건으로 판정하기 위해서다.
  - 배치가 끝나면 다시 쓰는 평가 컨테이너는 정지한다. 세션이 임시로 만든 컨테이너는 삭제한다.
  - 배치 전부터 있던 컨테이너는 건드리지 않는다.
  - **모든 평가·검수가 끝나면 평가 관련 컨테이너를 모두 삭제한다**(E6).

### E3. 평가 하네스 확장 (`eval/run_real.py`)

회차는 두 종류를 번갈아 돈다.

- **연쇄형(chain):** 빈 저장소에 문서에서 뽑은 의뢰서(BRIEF)를 두고 시작한다. 신규 → 기능 추가 → 리팩토링 → 고도화를 한 프로젝트에서 이어 수행한다.
- **실레거시형(real):** 실제 저장소 사본에서 기능 추가 → 리팩토링 → 고도화를 수행한다. 과제는 문서에서 뽑는다.

| 회차 | 문서 조회 | 종류 | 근거 문서 | 과제(자연어 요청의 내용) | 난이도 |
|---|---|---|---|---|---|
| 1 | 허용 | real | fastapi-default | 기능: 상품별 재고 조회·증감(슈퍼유저), 음수 409·잘못된 증감량 422, MySQL 동시성. 리팩토링: catalog 서비스가 Repository를 인자로 받게. 고도화: 커버리지 측정 대상 정정과 전후 수치 | 중 |
| 2 | 금지 | chain | g6 | 신규: 게시판 CMS(로그인·게시판·글쓰기·포인트, 화면과 API, 동기 DB)를 빈 폴더에서. 기능: 댓글. 리팩토링: 화면·API 공통 흐름. 고도화: 목록 성능 | 중 |
| 3 | 허용 | real | g6 | 기능: 게시판별 하루 글 수 제한(응답 계약 유지). 리팩토링: 게시글 작성 슬라이스를 서비스·Repository로(커밋 1회). 고도화: 비밀값 기동 검사·자동로그인 버그·의존성 고정 | 상 |
| 4 | 허용 | chain | fastapi-default | 신규: 상품·재고 API. 기능: 주문(재고 차감과 함께 성공·실패, 409). 리팩토링: Repository 주입. 고도화: 처리량·응답 시간 전후 비교 | 상 |
| 5 | 금지 | real | fastapi-default | 기능: 상품 목록 가격 범위 필터(422). 리팩토링: `main.py` 예외 처리·헬스 분리(OpenAPI 유지). 고도화: `config.py` 설정 분할(공개 이름 유지) | 최상 |
| 6 | 금지 | real | g6 | 기능: 댓글 금지어 거절. 리팩토링: 수정·삭제 슬라이스(커밋 1회). 고도화: async 경계 정리와 동시 요청 전후 비교 | 최상 |

- 회차의 원문 요청과 기대 조건은 `eval/real/cases.json`에 있다. context7은 MCP 인증 대기 상태라 미연결 대체 경로를 확인한다.
- 판정은 기존 `run_tracks.judge_stage` 항목을 그대로 쓴다: 필수 플러그인 호출, 조건부 근거 기록, 완료 확인, 질문 없음, 시간 내 종료, 단계 이동.
- **산출물 감사를 추가한다(Q-4).** 회차마다 다음을 `result.json`의 `audit`에 남긴다.
  - 테스트를 다시 실행한 결과
  - 추가된 커밋 수
  - 추적 ID(R-·F-·E-)
  - 변경 파일·줄 수
  - 기대 조건
- 기대 조건은 파일 이름이나 위치를 묻지 않는다. 이번 회차에 바뀐 파일(`changed`)에서 요청이 요구한 행동(예: 409, `min_price`)을 확인한다.
  - 문서 속 이름(예: `*inventory*`)이나 원래 있던 파일로 통과하는 조건은 쓰지 않는다. 범용 플러그인은 프로젝트 구조에 맞춰 이름을 정할 수 있어야 하기 때문이다.
- 회차 통과 = 모든 단계 PASS + 테스트 재실행 통과 + 산출물 감사의 필수 항목 충족.

### E4. 실행과 진단

- 판을 고정하고 1~6회차를 돈다. 병렬은 2개(real 회차는 무겁다).
- 실패는 셋으로 나눈다: 플러그인 결함(판 올림, 다시 셈), 하네스 오판(재판정), 환경(재실행).
- 5회 연속 통과가 모자라면 7회차부터 같은 표를 반복하되 슬라이스·후보를 바꿔 이어서 돈다.
- 실행 방식:
  - 실행기는 독립 프로세스로 띄우고 출력은 `sp-real-rN.log` 파일로 받는다. 도구 백그라운드 작업은 메모리 부족 등으로 종료될 수 있다.
  - 사용량 한도에 걸린 세션은 30분 간격으로 같은 세션을 다시 시작한다.
  - 판을 바꾸면 실행 중인 배치를 멈추고 새 배치로 처음부터 센다. 실행 중인 회차가 고친 파일을 바로 읽기 때문이다.

연속 통과는 판 L로 시작한 7차 배치에서 셌다. 진단 상세는 `RESULTS.md`의 진단 이력 표에 있다.

### E7. 설치 검증 — 완료

- 실전 평가는 `--plugin-dir`로 돌렸으므로, 사용자 설치 경로(마켓플레이스 추가 → 설치 → 새 세션)를 따로 확인한다. 사용자 전역 설정은 바꾸지 않도록 임시 프로젝트에 프로젝트 범위로 설치한다.
- 결과: 설치·로드·훅·제안 모드·`/stage-pilot:stage`·문서 앵커 모두 정상이다. 다른 워크플로 플러그인(crp-workflow)이 함께 켜져 있으면 트랙 추천이 밀릴 수 있다. 요청에 "stage-pilot으로"를 넣거나 프로젝트 단위로 끄면 해결된다. 이 내용을 매뉴얼에 적었다. 상세는 `RESULTS.md`의 설치 검증 절에 있다.

### E8. 후속 검증 — 완료

- 수행 모드 진입, 승인 대기 초안 적용, legacy-onboarding-manual 실사용, 생성 코드 품질 검토, GitHub 원격 설치를 확인했다. 상세는 `RESULTS.md`의 후속 검증 절에 있다.
